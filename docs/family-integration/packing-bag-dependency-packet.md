A refused item or category-batch restore may need a deleted bag restored first. A second ordinary bag save is correctly blocked; retrying the first child with different facts is not an acceptable workaround. D2b's `packingBagSession.test.ts` preserves and proves this restriction.

Read these implementations, `packingBagContract/Transport/CommandSession/Cohort`, existing item and category-batch restoration contracts, `retainedCommand`, `retainedRecovery`, queue locks/write-session owners, `offlineDb` mutation schema/export and current tests before editing. ## Bounded implementation

1. Add a dedicated owned dependency coordinator (`packingBagDependency.ts`, strict contract module if needed). It may represent exactly one blocked original item/batch command plus one explicitly requested `bag-restore` for a referenced deleted bag in the same Trip/source/published layer/current actor. All other bag actions and unrelated second writes remain refused. Check the child's actual observed bag relationship and authenticated deleted-parent observation. An arbitrary409, stored name or UI index is insufficient evidence of a parent dependency.
2. Preserve the child queue row and original envelope byte-for-byte. Persist the parent under its own operation UUID with a strict versioned dependency descriptor linking to the child's operation UUID and immutable original digest. Extend only the existing queue row contract/export/parser as needed; no new Supabase table or bag receipt store. A missing/mutated relationship, third row, crossed context, old unsupported descriptor or malformed row must refuse safely. Do not place dependent work on the generic queue replay path. Retain and export both originals during interruption/logout. Never convert existing one-row queues implicitly into a different intent.
3. Acquire the existing exclusive queue owner lock for proof, pair creation, delivery and acknowledgement. Verify the child's typed receipt first. If committed, reconcile that exact result and do not invent a dependency. For unknown child proof, let an explicitly confirmed parent restore obtain its own current observation/revision/collection and immutable original envelope. Retry/check the parent using its own typed receipt. A known committed parent can release only its own row; leave the child intact. On loss, cross-tab contention or process restart, recover the exact validated pair under the current owner before doing anything else.
4. After parent proof, inspect the original child receipt again. If it remains unknown, offer only an exact original retry when its original contract still permits it. A collection-bound batch observation becomes stale after parent restoration: surface that conflict and require a fresh explicit user decision. No automatic new UUID, reconstructed manifest or silent rebasing. Where the user deliberately abandons an uncommitted original, use the existing explicit retention/export/discard safeguards and prove no queued/server commit can race that decision; create a new command only from a fresh observation after that decision. Do not invent success for unknown work.
5. Update ordinary startup and planner recovery to recognize exactly the validated dependency pair, keeping single-row behavior unchanged. Pair receipt lookup must not require a fresh planner snapshot when that snapshot is itself blocked. Original actor and Trip/lifecycle/permission/session checks remain enforced by both SDK and database. Redacted proof can settle exact history but never authorize the next write.

Do not open native bag controls yet. Keep desktop/phone markup/styles, normal non-Family TREK paths, saved v1/v2/v3, original source guards and item/category semantics intact. Source paths outside Family modules or queue contracts need a small concrete justification. No generic multi-operation queue relaxation or broad auto-retry.
