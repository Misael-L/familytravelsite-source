## Findings that affect Family

1. **No new direct Journey storage model was found in this range.** There are no changed Journey/Memories paths, database entity paths, or browser database/repository/sync paths between these two immutable endpoints. Journey is mentioned indirectly by assistant handoff and shared geographic lookup changes. That is different from a new Journey feature/schema. This bounded source finding does not claim all upstream contracts or Family Journey functionality are complete.
2. **Planner and booking fixes are relevant.** 5.1.3 fixes phone day navigation, hotel check-in/out display and day retention when a time-only booking gets a partial edit. 5.1.4 fixes form reseeding during Trip refresh, Firefox drag/reorder, rapid day swipes and flights without airport endpoints losing their day/time. Preserve our form-owner/actor/revision/idempotency contracts while adopting the native fixes; changing a React effect alone does not establish correct Family command behavior.
3. **The shared reservation response gains three optional stay-time fields:** `accommodation_check_in`, `accommodation_check_in_end`, `accommodation_check_out`. Native cards fall back from explicit booking metadata to the linked stay. Review the actual Family normalized projection and saved read format through the real native consumers. Reuse existing canonical stay/timing facts where they represent those values; add a DB migration only if a demonstrated missing fact/constraint requires one. No automatic Supabase columns or tables follow from optional frontend DTO fields. Test omitted fields versus explicit null, real midnight, untimed days, notes-only edits, check-in windows and repeat visits.
4. **Vacay has a concrete Family adapter follow-up.** Upstream moved holiday requests to Nager.Holidays v4, while `vacayHandler.ts` still calls the legacy re-export of `family-backend/src/data/supabase/nagerHolidays.ts`, which uses `https://date.nager.at/api/v3`. Merging the Nest service does not modify this separate browser adapter. Upstream reports v3 retirement on 31 January 2027. The provider's [current API documentation](https://nagerholidays.com/api) documents v4 and browser CORS. Verify both country and holiday endpoints, normalize `nationalHoliday`/`subdivisionCodes` to the current Family holiday shape, and test real error/cancellation and regional behavior before rollout. Do not silently turn provider failure into a successful empty calendar. No new table is currently demonstrated for this provider migration; existing saved calendars/leave records must survive.
5. **Map categories and Atlas affect the connector backlog.** Bakeries/groceries are added to native map/tour categories. Our `/maps/pois` gap is still a gap; new pills do not implement their Family catalog query. F5 must account for the new keys with real typed venue identity, source permissions, coordinates and stored variants. Map existing food/taxonomy data only where it actually represents the category; do not fabricate venues or substitute city coordinates. The Atlas changes fix coastal-country matching/performance and Ireland county boundaries. Family owns its geographic data and hierarchy; an upstream asset or SQLite cache migration does not update Supabase geography or prove Family Atlas behavior. Preserve user marks and never infer that a marked province means every county was visited.
6. **Security/privacy changes need applicability checks, not blind database copying.** AirTrail now clears a stored key on a host change and saves settings transactionally. The inspected Family adapter advertises no AirTrail add-on and the Cloudflare configuration serves static assets; no executing AirTrail server path was identified in that profile. Keep the fix in the planned full upstream source reconciliation and recheck if that integration is ever enabled. This is not a new audit of live deployment exposure. Chat deletion now clears chat text. Collab is disabled here; do not apply chat-erasure semantics to recoverable Journey entries, Trip Trash, notes/history or backups.
7. **Auth, PWA, build and dependency changes require acceptance.** MFA code UI, native SSO handoff, the API public-path list, mobile layout and Vite/PWA/icon chunking change. Family currently uses Supabase password/MFA with OIDC/passkeys disabled; preserve those boundaries, deployed-version discovery, preboot recovery, owner-scoped caches and retained original work. The new `vite-plugin-pwa` major and lockfile are not harmless formatting changes. Upstream Brotli serving changes run in Nest; they do not configure Cloudflare static hosting. Native-app minimum-server versions do not require onboarding the separate iOS app into this website task.

## Database interpretation

The only added upstream DB migration files are `Migration20200101046370_a_deleted_chat_message_keeps_no_text.ts` and `Migration20200101046380_ireland_gained_its_counties.ts`. They are MikroORM/TREK database operations on chat and Atlas tables. They are not Supabase migrations, not an extra two to append to our existing forty, and not evidence that Journey needs a new table.

F2's observed hosted 88/local 128 migration versions, ten missing base APIs and one historical migration-name discrepancy remain real release prerequisites. They were not re-queried this turn. The source/adapter review found no requirement to abandon the existing normalized saved-location/visit, timing or recovery architecture. API compatibility still requires tests; absence of new upstream DDL is not proof that every response or behavior remains compatible.

## Recommended sequence

1. **F3a:** restore the verified real backup at its original schema into a new guarded, isolated local target. Resolve baseline/ledger provenance without editing hosted history. Preserve the backup and all old proof targets.
2. **F3b:** rehearse the existing exact forty canonical migrations on that copy, including data preservation, authorization, Trash/recovery and cleanup races. Diagnose failures before upstream merging. This validates the backend foundation we have already built.
3. **U05:** execute [controlled 5.1.4 reconciliation](trek-5.1.4-reconciliation-packet.md), branching from the latest complete Family candidate. Retain 5.1.2 and all packet history. Resolve source/contract overlaps, Family holiday adaptation and booking projection/command compatibility. No feature is enabled merely because an upstream menu or test exists.
4. Finish F4 publication hygiene and F5 core catalog/availability against the reconciled candidate. The bakery/grocery and geography requirements above refine F5; larger Atlas/Journey/Collab/provider features remain separate onboarding work.
5. **F3c and U05 final acceptance:** qualify the final default-profile build against the upgraded isolated target after those source repairs. Run affected tests during each change; reserve whole-candidate acceptance for the actual release tree. Then reconsider an integration-preview update with the correct backend, source publication and rollback companion. No production merge/deployment follows automatically.

This refines the original order: the baseline restore and backend rehearsal remain next, while final browser/release acceptance moves after the upstream reconciliation and required source repairs. No already qualified packet is discarded, and no old test result is relabelled as 5.1.4 acceptance.
