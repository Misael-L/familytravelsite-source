## Delivered contract

`PackingBagDependency` permits exactly one refused original item restore or category-batch restore plus one explicitly confirmed restore of its referenced deleted bag. It reads the child's authenticated Trash row/current batch observation, checks the actual bag relationship and matching full actor/Trip/lifecycle/scope/collection facts, and checks the child's typed receipt before preparing a separate parent UUID. A prepared draft is checked again before persistence and before delivery. A known committed child is reconciled instead of inventing a dependency. An arbitrary409 or display-only bag is insufficient.

The child's original envelope and complete queue row stay unchanged. The parent carries a strict version1 `familyPackingDependency` descriptor binding child operation UUID, envelope SHA256, whole-row SHA256, parent UUID, bag UUID and item witness (batch uses its existing original manifest). Hashes use typed canonical framing with ASCII-sorted keys, preserving insertion-order independence and present undefined fields distinctly from absent fields. Each parsed original row/descriptor is bounded to8MiB; existing bag request bounds still apply. Changed data, unsupported keys/format, a third row, wrong relationship or changed context refuses safely.

The parent alone uses queue format3, understood only by this dedicated coordinator. Generic queue replay remains on format2; existing commands and saved formats are not upgraded. The optional queue field is preserved as unknown data until the strict coordinator parses it. It grants no authority. No new Dexie table or global format migration was added.

Exclusive cross-tab queue ownership protects pair creation, delivery and acknowledgement. Startup recovery recognizes the exact pair without requiring a fresh planner snapshot. Normal planner reconciliation can prove the parent while still reporting the child unresolved. Bag SDK cohorts expose the coordinator through `packingBags.dependencies(trip)`. Parent response loss/restart/retirement is reconciled with the exact typed bag receipt, including a valid redacted committed proof. Unknown never means success. Parent acknowledgement removes only the parent, then ordinary child recovery can inspect/retry the unchanged original.

A small database-layer preservation marker keeps both rows out of generic replay, status normalization, broad retry and conflict overwrite/discard. Logout retains the pair exactly in its original account database, invalidates old owners and clears read caches; it does not reinterpret a descriptor. Future/invalid metadata is exportable and protected but cannot authorize a write. Generic unrelated queue and single-original behavior remain tested and unchanged.

## Remaining blocker, demonstrated rather than bypassed

The actual126 test `does not treat unknown receipt as cancellation: the same original can still commit later` reads an unknown child receipt, keeps the exact child queued, then delivers that same original later and observes a committed receipt. An unknown receipt cannot safely authorize dropping/replacing a request that another tab or an already-started request may still submit. Existing retained-work export/discard guards intentionally do not offer such unsafe abandonment.

Also, restoring a bag increments the collection revision. The original category-batch restore remains stale even though its bag dependency has been resolved. Its original remains retained and exportable; no automatic rebase, new UUID or reconstructed batch was introduced. Parent commands made stale by another actor need the same safe terminal decision.
