## Schema delta

Extend existing `public.packing_categories`, retaining UUID primary key, immutable `(id,trip_id,owner_person_id,created_at)`, compound `(trip_id,id)` key, current scope/name uniqueness `UNIQUE NULLS NOT DISTINCT(trip_id,owner_person_id,name)` using C collation, server-managed revision and timestamp. New fields:

- `retained_when_empty boolean NOT NULL DEFAULT true`: explicit display retention, independent of content rows.
- `sort_order bigint NOT NULL`: bounded `0..9007199254740991`, default 0 for compatibility; do not enforce uniqueness. Commands append under the existing Trip mutex, and reads break ties with category UUID.
- `deleted_at timestamptz NULL` and `deleted_by_person_id uuid NULL REFERENCES public.people(id) ON DELETE RESTRICT`, with `CHECK ((deleted_at IS NULL) = (deleted_by_person_id IS NULL))`. The actor must belong to the Trip's Family and is derived from current authorization, never accepted in caller values.
- Partial active-order index `(trip_id,owner_person_id,sort_order,id) WHERE deleted_at IS NULL`; partial `deleted_by_person_id` FK index; Trash paging index `(trip_id,deleted_at DESC,id DESC) WHERE deleted_at IS NOT NULL`. Preserve existing owner/item/category/assignment indexes and all FK deletion restrictions.

Initialize retention true only for categories with an existing active item, false for historical metadata-only categories; do not silently display historical orphans. Existing `...` items remain ordinary persisted content, unchanged. Deterministic per `(trip_id,owner_person_id)` initial order: first active item `(sort_order,item.id)`, then first historical item, then category creation/ID; use `row_number()-1`. Record all old item/category IDs, revisions, timestamps, raw labels, assignment provenance, receipts, graph/audit hashes before/after. This is metadata initialization, never permission to rewrite item ranks/content or media. Keep old revisions/timestamps stable during the controlled metadata backfill; subsequent actual state changes increment category revision once and update timestamp server-side. No-op transitions create a typed receipt without rewriting facts; do not assume collection revision increases by exactly one.

Preserve all-state name uniqueness. A dismissed or historical name remains reserved for its original identity. New creation with that name conflicts; the caller must explicitly retain/restore the known original record. Do not append invisible characters, strip existing Unicode or auto-merge identities. Empty raw `''` default categories remain compatible history; new named categories require 1–200 Unicode scalar characters and nonblank PostgreSQL-space-trimmed content without changing the submitted raw text.

## Lifecycle command and receipt contracts

`execute_family_trip_packing_category_lifecycle_v2(p_trip_id uuid,p_operation_id uuid,p_scope jsonb,p_action text,p_target_id uuid,p_expected_collection_revision bigint,p_observed_category jsonb,p_values jsonb) RETURNS jsonb`.

Require the original canonical published packing scope, a UUID operation/target, current direct `trip.packing.manage`, current Family/Person/MFA/session and Trip lifecycle, and bounded safe integer collection revision. Authenticate again after waiting. Acquire locks in the existing order: aggregate advisory `trip-recovery:` mutex → Trip row → packing-state row → category/item/assignment rows in deterministic ID order. Read/compare the complete original observation in the same transaction. [Consistent PostgreSQL lock ordering](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-DEADLOCKS) prevents inversions. Never rely on an AFTER/row trigger to repair an already inverted lock order.

Only four actions in C3a:

1. `category-create`: `p_observed_category = null`; unused client target UUID; values exactly `{name,visibility:'common'|'personal'}`. Derive null common owner or the current actor Person for own personal. Create retained, active metadata and append its owner lane sort key. Existing same-name metadata—including hidden/orphan/Trash—conflicts with PT409; do not return a different ID for the requested target or overwrite assignments.
2. `category-retain`: complete active original category, values `{}`, no live items and retention false. Set retention true, retaining ID/name/order/provenance. A known already-retained target is a no-op only with its actual full current observation. This is explicit reopening of unretained historical metadata, not a new identity.
3. `category-dismiss-empty`: complete active original category, values `{}`, zero active items under lock. Set deletion time/current actor, retaining all historical item references, rank, retention and assignments. A concurrent/hidden active item refuses the operation. A nonempty category is never partially emptied by this command.
4. `category-restore-empty`: complete trashed original category, values `{}`, zero active items. Clear deletion fields and set retention true on that same ID; do not restore items or reassign responsibility. Existing ineligible assignment provenance is preserved, never treated as a new eligible assignment.

Owner rules remain common/own personal only. Foreign personal visibility does not grant authoring. Do not accept `owner_person_id`, arbitrary actor, timestamps, ranks or fields outside the action schema. Invalid input is 22023; forbidden scope is 42501; stale collection/category/lifecycle, occupied identity/name and active-child dismissal are PT409; size/overflow is 54000. No semantic rebase or implicit merge. Preserve the existing upper bounds/Unicode validation.

Result exactly `{version:2,kind:'packing-category-lifecycle',trip_id,operation_id,scope,action,values,collection_revision,category,changed}`. `category` is the complete committed v2 observation and `changed` is boolean. Share the existing `(trip_id,actor_user_id,operation_id)` receipt namespace; hash all original scope/action/target/collection/category/values. Extend receipt action/domain CHECKs by explicit new action names, keep `category_id = target_id` for these four actions and retain its compound Trip FK. A repeated identical operation returns its original result after current authorization; changed domain/intent conflicts. Do not add an independent receipt table or rewrite old receipts/audit history.
