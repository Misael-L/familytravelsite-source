## Required behavior

A user must be able to deliberately cancel an unresolved creation or Add-to-day command and then start a corrected new intent. Cancellation is an authenticated server command with an authoritative outcome. It is not a local queue delete, a corrected replay of the old command, or a read that secretly saves something. A committed original must be acknowledged as committed; cancellation must never undo that saved location/visit or pretend it did not happen.

If current permission is unavailable, retain/export the original and explain the refusal. Do not interpret403, a timeout, a missing API or an unknown receipt as permission to discard it. Restoring authority may permit the same original to complete. A new corrected form receives a new operation only after the old original has a verified terminal outcome and its local preservation transaction succeeds.

### Serialize cancellation against execution

Recommended design: one private typed `family_auth.native_plan_cancellations` table, keyed by `(trip_id, actor_user_id, operation_id)`, holding the exact original request digest and a server cancellation timestamp. Reuse the existing typed creation digest framing (`native_plan_create`, original scope, original form); do not invent an unrelated cancellation identity. Store no credential or redundant raw media/form copy on the server. Align foreign keys and hard-purge behavior with the inspected existing receipt/Trip recovery lifecycle before finalizing DDL; never independently expire a tombstone while its old command could execute. No direct API table access or grant expansion.

Introduce a bounded cancellation RPC taking the original `p_trip_id`, `p_operation_id`, `p_scope` and `p_form`. Capture current actor/person/Family/layer and validate shape/bounds using the same authority rules as creation and receipt reading. Follow the existing creation lock order: current-session precheck, the same Trip recovery advisory lock/Trip row lock, then current locked session/permissions. Under that shared boundary, return an existing committed receipt unchanged, or insert/replay the cancellation fact for an as-yet-uncommitted original. Conflicting reuse of the UUID/digest must return PT409. Preserve real serialization/deadlock handling; do not catch all40001 errors.

The creation coordinator must check that cancellation fact under the same lock before it can create any child or receipt. Read receipt state and cancellation state without exposing the private tables. A cancellation-first race must make every delayed original retry refuse permanently; a creation-first race must make cancellation report committed. Both must never win. A response lost after cancellation must be safely discoverable after reload, without executing the original as a check.

Prefer an explicitly versioned outcome reader for the new `unknown | committed | cancelled` contract rather than silently changing the strict existing v1 response shape. Preserve safe behavior for old v1 callers, including refusing a cancelled original rather than falsely reporting successful creation. Keep the original creation response/input contract intact. Freeze exact fields, nullability, error codes, owner/ACL/RLS, indexes and ledger expectations before implementing the migration. Use the CLI-generated migration filename, two isolated upgrade rehearsals and real Auth/TOTP/PostgREST tests; no hosted or linked fallback.

## Acceptance matrix and stopping rules

- Real unknown, committed and cancelled outcomes; exact repeat cancellation; changed digest, other actor/Family/Trip and permission loss; current session expiration/deletion and MFA requirements; direct/propose/deny behavior for each supported layer.
- Two genuine concurrent HTTP commands for both race orders: cancel versus create. Verify result/receipt/tombstone counts, no partial child writes and no late execution of a cancelled original.
- Native desktop/phone creation and Add-to-day producers; persist/arm before network; slow replies and disabled controls; dropped cancellation/creation replies, timeout, cold reload, native logout/fresh sign-in, source/account/person/Family/layer switches and competing tabs.
- Read-only checks never execute or cancel unknown work. Terminal API missing/malformed/conflicting/redacted responses do not remove anything. Local archive failure or quota/full/corrupt/unknown schema leaves originals untouched.
- A deliberate corrected new form after verified cancellation creates exactly one new logical result with a new operation. Late delivery of the old cancelled command creates nothing. A cancellation that discovers committed creation causes no duplicate replacement and does not erase the saved object.
- Exact app source qualification, scoped lint without new warnings/suppressions, meaningful adapter/recovery regressions, typecheck and exact committed-source build; correct/wrong/missing-source artifact controls and real isolated browser acceptance. Keep all original/incoming rows, canonical source/index, old ledger arrays/permissions and service/evidence manifests.

If the server prerequisite is not ready, finish its bounded tests/handoff first and leave the cancellation control unavailable. Do not enable partial client cancellation. Stop only newly owned services and seal accepted proof and failed attempts. Full Q26 acceptance, other writer durability, dashboard recovery discoverability and independent backup restoration remain separate release gates.
