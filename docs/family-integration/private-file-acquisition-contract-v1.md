# U03-D16i — private-file acquisition contract v1

## Accepted boundary

This packet supplies an executable **acquisition primitive**, not persistent offline documents, a native saved-file provider, a new access grant, or whole-Trip preparation. `acquirePreparationFile` consumes an already admitted complete-v2 published read and its original `check`/asynchronous `verify` operations. A caller must supply the real source/account/Trip/queue/import/generation guard; passing arbitrary JSON with no-op checks is not application admission. There is deliberately no ordinary product consumer or new UI enablement here. The next packet must compose the existing online complete-read admission with saved-view and file-preview leases before exposing the primitive to a native control.

The existing preview provider remains the owner of signing, online authorization, temporary URLs and native preview behavior. `readObservedFileWithBody` extracts its existing observation-bound acquisition pipeline so preparation can opt into strict streamed consumption. `readObservedFile` delegates to the same pipeline with the original `response.blob()` policy. Existing online/offline previews and the JavaScript file-open handler retain their behavior; this packet does not silently tighten all existing previews or fill native IndexedDB stores.

## Identity and authorization

Selection is one active file from the admitted complete envelope. File UUID, Trip UUID, native identity binding and media manifest path must agree. The exact published generation, snapshot digest, source, actor/Family/person, owner generation and original deadline remain attached. Only canonical qualified loopback sources are accepted; hosted/ordinary activation remains off. Unsafe or ambiguous paths, absent/unrecognized MIME, oversized metadata and unsupported formats refuse.

A real repository session must agree with the saved actor/Family/person. `observeFile` requires the actual previously listed file reference and re-reads its active RLS metadata under the original repository and Trip contexts. A UUID alone is insufficient. Compare UUID, Trip, path, original name, declared size/MIME, uploader and creation time before signing and after consuming the response. Star/description/link changes are not a content identity. No service key or alternative Storage policy is used by the browser code.

The existing SDK creates the 120-second signature. The acquisition permits only the configured source's exact signed `trip-files` object path with one nonempty token and supported SDK query parameters. Requests omit cookies and reject redirects. No original/public/transform URL fallback, retries hidden as another file, cached-success fallback after denial, or signature persistence is allowed. Metadata/HTTP/access refusal propagates.

## Streaming and returned facts

An explicit `user-request` selects one file; no startup, background job or bulk downloader calls it. Metadata and decoded response bytes retain the existing **50 MiB** per-file ceiling. The reader consumes chunks, checks scope/cancellation between awaits, rejects overrun before retaining that chunk, and requires exact declared decoded byte count at EOF. MIME is normalized and must match a supported declared MIME. An identity representation's Content-Length must match; a compressed representation's encoded length is not treated as decoded length. Decoded chunks are always bounded. This is a bound on accepted/retained file content, not a promise about the browser decoder's peak process memory.

Missing or malformed headers/body, short content, stream failure, unsupported MIME, overrun and cancellation reject; there is no unbounded `blob()` fallback in this strict reader. Early header refusal cancels its response. Acquisition owns a calendar/monotonic deadline and a lightweight one-second original-read/context watch. A stalled response is cancelled on original expiry or scope retirement, and publication rechecks the deadline even if timers were delayed. The caller's AbortSignal also settles the operation promptly, including while SDK metadata/signing promises cannot themselves accept a signal; late SDK replies remain fenced and cannot publish or start byte acquisition. A stalled producer cannot keep cancellation waiting for its next chunk. Cleanup cancellation failures do not replace the original refusal. No DB transaction or queue lock crosses signing/network/body/hash work. The caller's verification runs before/after asynchronous phases, including hashing; expiry and generation replacement cannot publish successful bytes.

The returned in-memory Blob and `family.private-file-acquisition.v1` receipt contain the original scope/ownership/generation/digest, file UUID/path/creation time, observed SHA-256/size/MIME and original expiry. There is no signed URL/token/Blob URL in the receipt. The complete envelope, `mediaBytes=false`, queue, imports and original native bytes are not rewritten. Each deliberate acquisition makes fresh authorization/network reads; this primitive installs no retry cache or idempotency store.

## Content version and privacy decision

**Current metadata has no immutable server content version or server digest.** Uploads normally use a generated path with upsert disabled, but that client convention alone is not a database/Storage immutability guarantee. Before/after metadata agreement and a local SHA-256 prove what was observed; they do not prove that Storage and Postgres were read transactionally, detect a byte replacement with unchanged metadata, or authenticate a future version. The receipt explicitly says `serverContentVersion=unversioned` and `persisted=false`. Do not reinterpret it as a durable content-version grant.

No new CacheStorage, IndexedDB, localStorage, service-worker private cache, encrypted vault, receipt store or persistent private key is added. This primitive returns bytes to a trusted caller; it cannot erase copies retained by that caller or revoke server signatures. Cache ownership labels provide no encryption against same-origin script or someone with device access. The next bounded step should use a capped, generation-owned **RAM-only** lease pool, revoked/dropped on expiry, actor/session/Trip retirement and release. Cold restart should truthfully show documents unavailable until a separately reviewed durable-byte protocol exists. Durable private offline storage needs explicit device-consent/key-lifetime/retention design and reliable content-version reconciliation; neither should be smuggled into metadata cache migration.

## Evidence and limits

Unit cases cover strict selection/observed mismatch, original read replacement and expiry, denied HTTP without reuse, wrong SDK paths, actual split streams/overrun/underflow/compressed lengths, early rejection and pending-stream cancellation. Existing native preview tests remain unchanged. The existing separately fixture-gated live test is extended, keeping its original three assertion identities: real password/TOTP, Data API/RLS and Storage bytes plus strict streaming, actual preview lease and outsider denial. Its full-suite pending statuses remain pending unless the explicit disposable fixture is provided.

One older browser fixture declares a different size from its actual original PDF. Its rows/bytes are preserved; strict preparation must refuse it. A separate tiny 45-byte synthetic fixture supplies the positive live case. This discovery is not evidence of corruption in hosted user files. Browser compatibility checks use the actual freshly built App, installed SDK and worker; they qualify the unchanged current preview pipeline, not a new native saved-file feature. Full private saved-view/provider acceptance remains for the next packet.

No schema/SQL migration, production/preview/main/push/deployment, hosted settings/billing, dependency update, transformation/backfill, original backup/media or ignored ETL change. The existing guarded helper creates only a separate disposable synthetic family/Trip/file for live proof. Original fixtures and audit records remain retained.

Supabase documents the distinction between private RLS-controlled access and time-limited signatures in [Storage buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) and [private downloads](https://supabase.com/docs/guides/storage/serving/downloads). Signature lifetime and browser lease lifetime are different; changing Auth keys does not retroactively revoke issued Storage signatures. The current changelog requires no dependency/CLI change for this packet.
