## Boundaries that must remain explicit

Public stored catalog variants and private documents have different access rules. An ordinary public object URL needs no private signing token. Private metadata, signed URLs and downloaded bytes are three different things. Supabase documents public downloads and private authenticated/signed downloads, and notes that individual issued signed URLs cannot be revoked directly: [Storage downloads and signed URLs](https://supabase.com/docs/guides/storage/serving/downloads). Signing expiry is not a lease on an already downloaded Blob. This review proposes no key rotation or hosted setting change.

Two implementation hazards were found **behind the current Family preparation refusal**, not reproduced as current Family leaks:

- Generic `cacheFilesForTrip` uses URL-keyed native blobs without a Family complete-generation/content receipt, and has no explicit current-session check after awaiting the body immediately before its put. Generic preparation also catches some component failures without a per-file readiness result. Do not remove the planner guard and call this a connected Family downloader.
- The private cached-preview reader checks native Trip/file/blob relationships and session context, but is not tied to the complete-read fifteen-minute lease, content revision/digest or a supported Family private-download receipt. There is no qualified Family preparation producer for those rows. Before adding one, define read leases, identity, failure/cancellation, revocation/eviction and original-work protection together.

These are prerequisites for **enabling those byte paths**. They are not evidence that already qualified metadata-only reading is broken, and optional private downloads are not a required dependency of a clearly limited metadata-only release. Public bytes must not be coupled to private-file readiness or new database tables merely to reuse a counter.
