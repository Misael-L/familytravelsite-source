## Blocker 1 — an open Family tab has no deployed-release version feed

Actual `applicationHandler.ts` returns the running bundle's `__TREK_UI_VERSION__` for `/auth/app-config`. `App.tsx` consumes that version at launch. Native TREK normally receives subsequent version announcements from socket welcome messages. Family replaces that socket with `realtimeBridge.ts`, which handles Family notifications/Trip invalidation but supplies no deployment version. A service-worker controller change alone does not update `serverVersionStore`.

In both local Chromium desktop and phone profiles, actual A App/SDK password/TOTP/worker load; B is then served at the same origin, with a distinct built release version and hashed entry. The actual B worker activates and precaches B. A still reports version `5.1.2`, continues running its A entry, and displays no native new-version notice in the bounded 2.5-second post-activation observation. The source review establishes the missing feed; the finite observation does not claim an infinite wait. Explicit reload boots B and reports `5.1.2-d16l-next`. Native typed search text survives worker replacement; original synthetic command fields and import bytes remain exact through explicit reload.

This is missing Family deployment wiring, not a reason to alter native notice markup or force an automatic mid-edit reload. It also needs a real per-release build identifier: using only the upstream package version cannot distinguish consecutive Family deployments based on the same TREK version.
