# U04-C2 — stable packing category contract

Status: design and local audit accepted only after the accompanying receipts pass. This document specifies the server foundation to build next; it does **not** claim that category tables, category RPCs, rename, assignments, notifications or hosted migrations have been implemented. The current disposable chain remains 120. Existing native item/group controls retain their qualified behavior.

## 1. Evidence and problem

TREK 5.1.2 supplies category labels to desktop/phone grouping and legacy rename/assignee helpers. Current Family storage repeats a raw category string on `packing_items`. `packing_category_assignees` keys assignments by Trip and that string. A common list, the current Person's private list and another Person's private list can therefore share a label without having the same ownership. A label change cannot safely be modeled as a Trip-wide loop over matching items.

The local audit exercises actual stored rows and Auth/TOTP/PostgREST: identical labels cross these scopes; current assignment metadata is Trip-wide; an immutable trashed item refuses category-text updates; separate trusted legacy statements can partially rename or lose an assignment set on later failure; a transaction rolls back that set; common records may have a historical non-null owner; assignment changes invalidate stale collection observations; and historical assignment labels may exceed the item-name bound. Real denied/propose-only/AAL1 attempts stay denied. The trusted legacy-statement witnesses describe a primitive hazard, **not an enabled raw web writer**.

The rollback-only temporary-table prototype proves stable scoped identity, exact label comparisons, composite relationships, common-only assignments, rename without rewriting child/Trash facts, collision rejection and restricted raw access. It deliberately uses temporary parent mirrors because PostgreSQL temporary foreign keys cannot reference permanent tables. It does **not** qualify production category RPCs, RLS, migration/backfill, compatibility or UI cutover. See the sealed audit and prototype, rather than interpreting a structural test as feature completion.

The audit also exposed a frontend defect: reserved strings could disappear as object keys, become inherited assignee values, or begin collapsed on phone. The scoped repair uses `Object.fromEntries` and own-property lookups; names remain ordinary text. It changes no layout, styles or feature permission.

## 2. Identity and exact text

Introduce `public.packing_categories` with these proposed columns and rules:

- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`.
- `trip_id uuid NOT NULL REFERENCES public.trips(id) ON DELETE RESTRICT`.
- `owner_person_id uuid NULL REFERENCES public.people(id) ON DELETE RESTRICT`. NULL means common; non-null means that Person's personal category. Context/ownership is immutable.
- `name text COLLATE "C" NOT NULL`, `CHECK (char_length(name) <= 200)`. Empty text is the unlabelled default; a literal `Other` is a different value. Persist no translated display name.
- `revision bigint NOT NULL DEFAULT 1`, constrained to 1 through 9007199254740991, managed by the server. Reject overflow rather than round in JavaScript.
- `created_at timestamptz NOT NULL DEFAULT now()` and `updated_at timestamptz NOT NULL DEFAULT now()`, server managed.
- `UNIQUE (trip_id, id)` for composite references; `UNIQUE NULLS NOT DISTINCT (trip_id, owner_person_id, name)` for exact name uniqueness within one ownership scope. PostgreSQL 17 supports this directly.

Names preserve case, whitespace and Unicode code points, including composed/decomposed forms and reserved JavaScript keys. Do not lowercase, trim, truncate, normalize Unicode, substitute display labels or count UTF-8 bytes as characters during migration. PostgreSQL rejects NUL in text. New rename commands require 1–200 characters; the native composer may trim its own input before capturing intent, but the server never silently rewrites the captured name. The empty default remains representable by the foundation even though the first rename UI need not create it.

An item belongs to exactly one category. Add `packing_items.category_id uuid`, backfill safely, then make it NOT NULL with `(trip_id, category_id) REFERENCES packing_categories(trip_id, id) ON DELETE RESTRICT`. A database guard enforces common item → common category and private item → same owner's category. Classify scope using `is_private`; a historical common item's `owner_person_id` is not proof that it is private and must not be cleared as incidental cleanup.

Final normalized storage has one category name on the category entity. The existing item label remains temporarily as an explicitly derived compatibility bridge; it is not a second source of identity. Do not drop it until all old readers/writers/retained work are classified and retired. First-class category create/reorder/Trash is separate. Retain empty category metadata for restores and receipts. Do not invent a hidden item merely to create a new normalized category; equally, do not delete existing items named `...` without explicit provenance classification.

## 3. Assignment is responsibility, not access

Introduce `public.packing_category_assignments` with `trip_id uuid NOT NULL`, `category_id uuid NOT NULL`, `person_id uuid NOT NULL`, primary key `(trip_id, category_id, person_id)`, the composite category FK above and a Person FK, both RESTRICT. Add nullable `assigned_at timestamptz` and `assigned_by_person_id uuid REFERENCES people(id) ON DELETE RESTRICT`: both NULL for unknown historical provenance, both non-null for newly created assignments. Do not fabricate historical actors or timestamps.

The first qualified assignment operation applies **only to common categories**. Personal ownership, contributors and responsibility are different concepts. Sharing a personal item does not give the recipient authority over its hidden siblings or its whole category. Personal assignee menus remain gated until a separate contract exists.

Require the existing direct `trip.packing.manage` permission and current role/MFA rules. New assignees must be eligible active travelers in the same Trip/Family; an eligible guest Person need not have an Auth account. Existing assignments whose Person later becomes ineligible remain historical responsibility metadata and may be removed. They cannot be newly added until eligibility returns. Assignment never grants Trip/item visibility, creates membership, invites a user or sends a notification.

Replace assignments by set difference in one transaction. Preserve unchanged links/provenance; validate additions before deleting anything. An identical desired set is a no-op with an idempotency receipt, without revision/audit/notification churn. Upstream notifications need a separately qualified delivery connector/outbox; no speculative delivery side effects here.

Index foreign-key lookup paths not already covered by a leading unique/primary-key prefix: category owner, item `(trip_id, category_id)`, assignment Person and assigned-by Person. The composite assignment primary key already covers category lookups. Measure real bounded joins, RLS and Trash histories before adding speculative indexes. No partitioning or global JSON category document is justified at this scale.

## 4. Meaning of rename and deletion

Rename changes one category entity across item statuses. It is not the status-filtered Check All/Delete List operation from C1c. A direct manager may rename a common category or their own personal category. A contributor to a visible foreign private item cannot rename the foreign category. Keep the existing authority and parent-lifecycle checks.

A native displayed group may combine different category identities: the raw empty default with literal `Other`, or same-name lists owned by different people. Such a heading is ambiguous. No first-match lookup, silent merge, owner inference or enumeration of hidden peer items is permitted. Rename/assignment actions remain gated or return a clear conflict until the consumer selects one category ID. A same-scope target-name collision is 409; merge is a different future command. The first release must not automatically merge lists.

Rename preserves item IDs, category IDs, item ownership, bags, order, checked/count/weight, private access, assignments and immutable trashed item facts. A restored item refers to its original category ID and displays that category's current name. Historical command receipts retain historical names and cannot publish an old name as current state.

No standalone category physical delete is exposed. Native Delete List remains the qualified observed item-group Trash command; deleting items does not cascade away category metadata or assignments. Trip Trash/root restore keeps the whole graph, category receipts and assignment provenance. Eventual permanent purge must account for these relationships explicitly under the aggregate recovery/retention policy; RESTRICT prevents accidental cascade. Shared People/catalog rows and Storage bytes are unaffected.

## 5. Classified migration and v1 coexistence

The next server packet must prove this bridge before new metadata controls can be enabled:

1. Preflight all live **and trashed** items, historical assignment labels, scoped duplicates, invalid Person/Family relationships, code-point limits and query/transaction size. Resolve or report unsupported legacy values; do not silently truncate or guess. Export a classification report containing counts and synthetic identifiers, not private production data.
2. Construct categories from `(trip_id, CASE WHEN is_private THEN owner_person_id ELSE NULL END, raw_category)`. Link every item without changing its existing facts/revisions/timestamps. Current global Trip-label assignees map once to a **common category**, even if it has no common live item. Never clone them into private categories merely because labels match. Preserve the old mapping for review/history.
3. Adding a column and updating trashed rows will currently invoke `ab_packing_v1_version` and fail. The six actual triggers are `aa_trip_aggregate_child`, `ab_packing_v1_version`, `ac_packing_v1_owner`, `packing_items_set_updated_at`, `packing_v1_audit` and `packing_v1_collection`. Their definitions/functions and old-row projections must be pinned before writing the migration. Under a bounded transaction and explicit deterministic table locks, narrowly suspend only the reviewed UPDATE triggers proven necessary for relationship-only backfill; restore **every original trigger state** before commit. Never use `DISABLE TRIGGER ALL`, `session_replication_role`, a persistent bypass flag or reduced RLS/grants. A deliberately late failure must roll back schema/data/trigger states. The exact minimal allowlist is an implementation prerequisite based on actual function bodies, not permission to disable all six.
4. V1 create/update resolves the exact Trip/privacy-owner/raw-label key inside the existing packing/Trip mutex. V1 readers serialize their strict old shape explicitly, deriving current label through category identity and omitting new columns. Group selectors join canonical categories instead of stale cached text. New category and item projections come from one consistent database read.
5. A future rename updates category metadata and only **active** compatibility item labels in the same transaction. Those active items advance revisions under reviewed command semantics so a retained v1 editor cannot write the old label back. Trashed rows remain unchanged. On an actual Restore, a narrowly reviewed restore path synchronizes the compatibility label while retaining category ID, returning the final server row/revision. Do not use a global bypass of the version trigger.
6. Every effective metadata or assignment change advances the existing Trip packing collection observation under the same lock order as item/group commands and Trip recovery. A stale menu/editor/queue original conflicts. No-op changes only record their receipt. Keep opaque revisions within JavaScript's exact integer bound.
7. Preserve all old operation IDs, payload/digest/receipt bytes, source/user/Person/Family/Trip/layer/lifecycle ownership and queue namespaces. Never mutate an uncertain retained original to add IDs or choose a replacement operation. Old known receipts remain inspectable; unknown remains uncertain. Incompatible retained work is reviewable/exportable, never silently discarded/rebased/replayed.

All 120 historical migration sources remain exact. Create one new migration with the installed pinned Supabase CLI only in the server packet, then rehearse on the marked disposable stack. No hosted migration is authorized here. The 120-only runners must refuse the new chain until new guarded runners explicitly qualify it. Existing v1 behavior is not preserved by merely creating tables: wrappers, serializers, groups, restore, exports, whole-Trip offline capture and all root recovery ownership paths need the same coordinated foundation.

## 6. Proposed additive API shapes

These names/payloads are proposed contracts, **not deployed endpoints**. Keep the existing item/group packet format and callers intact; category metadata gets its own domain API.

`get_family_trip_packing_with_categories_v1(p_trip_id uuid) -> jsonb` returns exact root keys `version`, `scope`, `collection_revision`, `packing`, `categories`, `item_categories`, `people`. `version=1`; `scope` is the existing bound Family scope; `packing` is the unchanged strict current v1 packet. Each `item_categories` entry is exactly `{item_id,category_id}` for an authorized returned live item. Category entries contain `id,trip_id,owner_person_id,name,revision,created_at,updated_at,assignments`; each assignment is `{person_id,assigned_at,assigned_by_person_id}`. `people` contains only referenced, authorized Person facts `{id,display_name,is_guest,eligible}` required for these returned rows/assignments. Eligibility is contextual to this Trip and may be false for retained history. Resolve the existing Person display-name column in the serializer rather than presume a new people column.

Return only categories referenced by authorized returned items; do not enumerate private history/empty peer categories through a global dictionary. Empty-category lookup/create is a separately authorized later API. Each array has deterministic UUID ordering, assignments by Person ID, item mappings by item ID; the existing packing packet keeps its established ordering. Capture one statement snapshot/scope/collection; no mismatched separate fetches. The current live-item bound is 2,000 and the complete serialized result bound is 8 MiB UTF-8. Exceeding a bound refuses explicitly; never silently truncate. Test whether the extra metadata reaches the bound before adopting constants in code.

`execute_family_trip_packing_category_v1(p_trip_id uuid, p_operation_id uuid, p_scope jsonb, p_action text, p_expected_collection_revision bigint, p_observed_category jsonb, p_values jsonb) -> jsonb` supports only `category-rename` and `category-assignees` initially. No unchecked generic JSON patch. `p_observed_category` is exactly `{id,trip_id,owner_person_id,name,revision,created_at,updated_at,assignments}` from the coupled reader, assignments sorted as above. Expected scope, lifecycle, collection and complete category/assignment original must match before writing. Capture an operation UUID once per deliberate submission; identical retries use the exact original.

For rename, values is exactly `{name: string}` (1–200 PostgreSQL characters). For assignment, exactly `{person_ids: UUID[]}` sorted/unique, limited to 2,000 IDs and 262,144 UTF-8 JSON bytes, also validated against the actual Trip roster. Unknown fields, duplicate IDs or malformed originals are refused. No whole-item enumeration is needed for an **entity metadata** operation when the actor has authority over that category; collection and category observations protect its whole scope. Do not leak hidden sibling IDs in conflicts or results.

Successful acknowledgement keys: `version,kind,trip_id,operation_id,scope,action,values,collection_revision,category,changed_item_revisions`, with `version=1`, `kind="packing-category"`, the resulting category in the same strict shape, and `changed_item_revisions` sorted `{item_id,revision}` for authorized active compatibility rows only (bounded 2,000). The acknowledgement is commitment proof; publish data only after a fresh guarded coupled canonical read. Review larger histories independently of the live bound. No-op result has unchanged category/collection and an empty changed-item array.

`get_family_trip_packing_category_receipt_v1(p_trip_id uuid,p_operation_id uuid) -> jsonb` uses the established committed/unknown/redacted receipt envelope and authorization/lifecycle policy, with domain `kind="packing-category"`; it does not turn a historical original into current read authority. Keep owner/source/cohort/session checks, online recovery gates and privacy redaction. A wrong-domain operation is malformed (22023); permission denial is 42501/403, stale/conflicting original or target-name collision uses the established PT409/409 envelope, invalid payload 22023, bounds 54000, and unsupported capability 0A000. Do not publish raw database exception details. No new UI error vocabulary is needed.

## 7. One atomic command, one globally owned operation

Reuse the private ledger `family_auth.packing_command_receipts` and its existing `(trip_id, actor_user_id, operation_id)` namespace so category/item/group operation reuse conflicts. The generic existing `target_id uuid` is not a foreign key. Add nullable `category_id uuid REFERENCES packing_categories(id) ON DELETE RESTRICT`; new category actions require `target_id=category_id` and non-null category ID, old actions retain NULL category ID. Extend the action constraint/dispatchers deliberately. Keep old row bodies/digests byte-exact; no historical rewrite or accidental item lookup for a category target.

Private immutable receipts record original intent, before/after category and assignment provenance. Shared coarse audit records must not embed private labels/Person IDs/item IDs. Define current visibility and redaction for every receipt dispatcher; the structural prototype alone does not establish them.

Lock order: follow the current aggregate Trip lifecycle lock, packing collection lock, ledger operation reservation, category and affected active item rows in deterministic ID order; validate again after locks. C2a must confirm this matches actual existing helpers before coding, avoiding an inverted extra category-first path. Collision or late trigger failure rolls back category/assignments/compatibility labels/revisions/collection/audit/receipt together. Duplicate submission returns the same saved result without another effect; a reused operation with changed action/original/scope/values conflicts. A concurrent group command observes either complete before or complete after state. Different categories may initially serialize on the existing Trip collection lock; correctness beats premature finer-grained concurrency.

## 8. Database authorization and lifecycle

Use the established public SECURITY INVOKER wrappers and non-exposed validating SECURITY DEFINER internals with `search_path=''`, fully qualified objects, `auth.uid()`/session binding, direct Family permission and role-specific MFA. Revoke default PUBLIC execution and grant only reviewed wrappers to the required authenticated role. Raw category/junction DML is revoked from client roles, including the exposed service role; internal owners are narrowly controlled. RLS remains defense in depth, not an alternative to command validation. No caller-supplied actor identity or service bypass.

Common metadata is available to an authorized Trip reader. A personal category is visible to its owner; a recipient who can see an item may receive that item's necessary category label/ID, without access to other items/assignees/hidden history or rename authority over the category. Assignees themselves do not expand access. Denied/propose-only and AAL1 reviewer/owner sessions must fail real commands, not just hide buttons. Parent Trash, stale lifecycle/layer, revoked membership and source/account changes refuse as they do today. No proposal conversion or automatic replay is introduced.

## 10. References and scope

Architecture uses PostgreSQL 17 [constraints and NULLS NOT DISTINCT](https://www.postgresql.org/docs/17/ddl-constraints.html), [transaction semantics](https://www.postgresql.org/docs/17/tutorial-transactions.html), Supabase [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and [function security/grants](https://supabase.com/docs/guides/database/functions). The installed database is PostgreSQL 17.11. This is a recommendation grounded in current business behavior, not a transcription of native item loops. Existing UUIDv4 conventions suit this small relation; no extension, dependency upgrade, partition or new role hierarchy is required.

Local only: no push/main merge, hosted preview/production deployment, hosted SQL/settings/billing, transformations/backfill, backup rewrite or ignored ETL changes. Evidence is not a backup or independent recovery proof. Incremental backup scheduling and off-device restore remain separately deferred.
