## Canonical migration and read boundary

Additive migration 133, `20261113234914_coherent_booking_stay_read.sql`, was scaffolded using pinned Supabase CLI 2.109.1. Its final SHA256 is `b52d662f2f94098343e8d7396d26bda8ad30271b5faed883deda14989a773c4b`. It adds three functions and no tables, writers or direct grants. All 132 historical migration sources/ledger entries and all 584 existing public/Family function definitions, owners and ACLs remain exact. Exact SQL and local test/guard review copies are in `docs/family-integration/supported-core-readiness/backend133` in the website checkout. The canonical repository's protected mixed index was not staged or committed.

`public.get_family_trip_booking_view_v2(uuid)` returns one complete published planner/booking/stay generation. A STABLE private helper reads the planner v1, booking v1, active stay view and retained stay links under one MVCC content snapshot. It compares their Trip revisions and retains their actual UUID identities, calendar, revisions and full source facts. A VOLATILE public wrapper checks current session, expiry, Family/person membership and Trip assurance before and after that content read. This permits an old but wholly coherent snapshot after a concurrent content change; it refuses authority revoked while the read waits. There is no content mutation, fake lock-based snapshot or pair of independent HTTP calls treated as coherent because their root revisions happen to match.

The version-2 envelope contains `completeness: complete`, published planner, extended booking rows and active stays. Booking rows add explicit active/retained stay identity and `timing_state` derived from real `timing_kind` values (NULL/legacy_unclassified, untimed, timed). Calendar dates are separate facts; there is no invented `date_only` discriminator. Genuine midnight, original timestamp strings, microseconds, named zones, unknown clocks and overnight windows are preserved. Stays without bookings, bookings without stays, repeated stays, same-day stays and dates outside the Trip calendar remain valid canonical facts. A retained link exposes identity only, not a trashed stay's private notes/content.

Read authorization inherits existing Family assurance and published access, without demanding Direct writer rights. The new public RPC is executable only by authenticated clients; private helpers are revoked from public/anon/authenticated/service roles. All three SECURITY DEFINER functions use an empty fixed search path. Existing row/byte limits are retained and the combined result is bounded to 8 MiB; exceeding a limit refuses the whole view, never truncates it.

The version-2 capabilities remain `read: true`, `native_read: false`, `native_write: false`, `confirmed_timing_write: false`. These report the canonical read contract's actual readiness. Later native admission must be a separately qualified complete contract; it cannot simply flip these flags, pass v2 through a v1 consumer or relabel a v3 snapshot.

## Website contract

The installed browser Supabase client now has one allowlisted SDK read and an explicit private GET handler at `/trips/:trip/family/booking-stay-view-v2`. The actual plan dispatcher routes this namespace. It accepts no query/body/non-GET variants and makes exactly one canonical RPC, with no raw-table, service-client, old-reader or cache fallback. Missing API, denied/expired scope, offline and overbound responses remain failures.

The strict adapter checks canonical identity, complete shape, all calendar/revision relationships, active/retained link uniqueness, lodging/booking consistency and exact nested source facts. JSON validation cannot silently strip unknown fields. Source, account/session, Family/person, selected Trip/layer, registry identity and abort fences surround asynchronous work. It publishes neither a planner store nor Dexie/saved cache generation. The identity registry adds only the pure `isScopedTo(userId)` predicate; it grants no access or new aliases.

`nativeStayReadiness` is a **pure qualification candidate**, not a native API activation or complete planner readiness check. It projects stays through the actual upstream Accommodation schema only when every active stay can be represented. Stable stay, saved-lodging, Trip and day namespaces remain separate; source notes/clocks and explicitly linked confirmation/title are retained. Images remain placeholders here and no media request is made.

The consumer audit found real native limits: Accommodation requires both numeric start/end Trip-day IDs and cannot express next-day check-in-window offset or subminute clocks. Those cases return `unsupported` with original stay UUIDs and concrete reasons: arrival/departure outside calendar, overnight check-in window, subminute clock. No stay is silently omitted and no day, time or city-centre substitute is manufactured. Readiness `ready` applies only to the stay projection; complete planner permissions, content generation and consumer readiness must also pass before UI use.
