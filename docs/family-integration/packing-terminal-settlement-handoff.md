## Atomic local preservation and pair ownership

The original queue row, companion row, exact row digest, explicit decision time and server proof live in a bounded preservation-only record at reserved `syncMeta.tripId=-2`. No IndexedDB schema/store/version changed. The archive permits at most1000 entries and32MiB encoded data; unexportable or over-bound data refuses settlement before removal. It is not a read cache, executable queue or automatic replay/import protocol.

Pending decision and original are saved before network cancellation. Under the original account/source/Trip queue lock, settlement re-reads the exact row/cohort and archive generation, verifies a freshly authenticated terminal proof/current scope, then atomically archives the outcome and removes only that exact row. A terminal result never publishes a historical acknowledgment as current packing state. Reconciliation refreshes a canonical current publication. Cooperative browser locks are not relied upon to revoke an older tab: the unchanged127 server terminal namespace arbitrates delayed originals atomically.

Cancelling a parent preserves its child unchanged. Cancelling a child preserves the format3 parent descriptor unchanged. A remaining parent may use the archived child only after exact pair/hash validation and fresh typed child-terminal lookup. Generic queue flush does not replay originals while cancellation is armed. A new packing command cannot slip in when an older tab has removed the queue row but the cancellation is still pending. Missing, changed, unknown-version or conflicting archival data never authorizes destructive cleanup.

## Replacement is a new explicit decision

`prepareReplacement(id)` requires a settled archived original, a fresh authenticated terminal lookup and no other unresolved packing work for the Trip. It reads a fresh complete bag/category-batch observation or current item Trash record and generates a distinct operation UUID. The returned `submit()` is separate; it rechecks context, archive, queue and observation, retains the new intent before sending, and uses existing typed command/acknowledgment handling. Changed facts refuse rather than automatically rebasing. The archived original's scope, observation, revisions, order and operation UUID remain unchanged. Parent restoration does not automatically replace or retry a stale category-batch restore.
