## What the current controls actually do

1. **Add category is enabled**, with direct packing permission: desktop uses the native name dialog; phone uses its name composer in edit/empty mode. Both call `usePackingItemActions.addNewCategory` (line 260), which sends an ordinary observed item create with `name: '...'`. Duplicate labels append U+200B invisibly. This is existing native behavior carried into the integration, not a normalized empty-category API. The row is genuinely persisted and counted in progress; filling it updates that same item ID. A deliberate second command can create another sentinel. One retried operation remains idempotent.
2. **A truly empty category is not represented.** `packing_with_categories_entry` selects categories only from readable active items (`20261111234537_normalized_trip_packing_categories.sql:968`). A category row with no active item is retained in storage but absent from the strict v1 coupled packet. The TypeScript v1 validator also requires every returned category to be referenced. `packingCategoryOrder` and `groupPackingItems` consume only item rows. These facts require a versioned read/projection change; changing a menu flag cannot solve them.
3. **Deleting the last real Family item is recoverable item Trash**, not the native legacy conversion to a sentinel (`usePackingItemActions.ts:192`). Its category disappears from the item-derived view while its category identity and assignments remain in storage. Restoring the item brings back the same category ID. No category Trash/restore lifecycle exists. Physical category deletion is explicitly refused. Existing group Trash/clear-completed operate on their observed item selection; they do not delete the category entity.
4. **Category card drag is gated separately.** `PackingListPanelList.tsx` supplies a category drag handle only when `canEditGroups` passes, which remains false in the Family cohort. Native desktop card movement calls `itemOrderWithCategoryMoved`: it permutes item blocks, placing the other view after the moved view. There is no category-position column. Phone 5.1.2 has no equivalent category drag control; this is upstream presentation, not a missing backend connection.
5. **Item ordering already has an atomic API.** `execute_family_trip_packing_v1` requires every currently visible active item exactly once plus the observed collection revision. It preserves hidden logical slots. Partial/filter-only lists are refused. Within-category item drag captures its original complete observation and fills the same slots. This can order nonempty categories by first appearance; it cannot remember an empty category or order category metadata independently of item ranks.
6. **Moving one item and renaming a category are different.** Native category selection updates one item's category via its observed item binding. The database resolves a category in that item's visibility/owner scope; other items and category IDs are not merged. Native legacy rename is an item loop and remains refused; accepted Family rename uses its transactional category API. Renaming into an occupied or historical empty name conflicts. There is no native explicit merge action to connect; a future merge requires its own domain contract, not a label rewrite.

## Recommended architecture and rejected shortcuts

Keep `packing_categories` as the category entity and its existing compound item FK, exact raw-name/owner uniqueness, assignment provenance and shared receipt namespace. Extend that table with explicit empty retention, a stable category sort key and recoverable lifecycle. A second category table, generic JSON position store, Unicode-name rewriting or permanently saving fake packing rows would add competing identities or corrupt content/progress semantics. New nullable deletion fields must have paired constraints; reference fields require indexes. Cross-table ownership uses validated relationships/triggers, not a CHECK that queries another table. See [PostgreSQL 17 constraints](https://www.postgresql.org/docs/17/ddl-constraints.html).

An item named `...` is ambiguous historical content. Neither its name nor a generic v1 create receipt proves that it was only a UI sentinel. Preserve every existing row, ID, weight, membership and audit link. Do not mass-delete/convert these rows. New empty states should be projection-only native placeholder rows marked with category identity and no persistent item identity; all item, queue and export paths must distinguish them from genuine stored items. No virtual row may enter `packing_items` or masquerade as `family_packing`.

Positions are sort keys, not identifiers: order by `(sort_order,id)` within a common or personal-owner lane. Ties are valid, deterministic and useful for safe compatibility writes. No unnecessary position-uniqueness constraint or fractional-ranking framework is needed at the bounded 2,000-category scale. Category reorder will later name a complete authorized category lane, preserve hidden/foreign lanes and leave every item rank unchanged. Keep existing item reorder for item order. Do not enable a new category drag until this distinction is tested.
