## Recommended model and alternatives

Keep a **booking** as a provider reservation and a **stay** as a planned lodging block. A stay may be planned without a confirmed booking; a booking can exist before its lodging is put on the plan. Shared catalog hotels and trip-owned saved locations retain their own identities. Several stays at the same hotel are valid; no location/date deduplication rule is introduced.

A read-only view over existing hotel reservations could expose a limited subset, but cannot support independent planned stays or safely resolve unknown clock provenance. Copying all native tables would repeat day-bound dates, mirrored mutable facts and destructive cascades. Use an explicit normalized stay entity and optional booking association instead. This is new domain support, not three convenience columns added to fit a DTO. Do not automatically create or classify stays from existing bookings in this packet.

## Proposed schema contract

These names/types are the target for a reviewed additive migration. Create its filename using the pinned Supabase CLI, then validate on a new guarded schema129 derivative. Do not edit historical migrations or ledger rows.

1. **public.trip_stays**: id uuid PK/default gen_random_uuid; trip_id/family_id uuid required with FK to trips(id,family_id); location_id uuid required with FK(location_id,trip_id) to the existing unique trip_plan_locations(id,trip_id); arrival_date/departure_date date required and finite, departure>=arrival. Equal dates represent a same-day lodging block; no overnight stay is fabricated. Dates remain facts even when a matching planning day is removed. No persisted start/end day aliases are required; map only exact same-Trip civil dates to native day IDs at read time. A stay location must be a saved catalog hotel or an explicitly named manual lodging location; reject catalog city/country/food/experience identities. Enforce this with locked cross-row guards on both stay writes and referenced-location source changes, not just a frontend filter.
2. Its clocks are check_in_time, check_in_window_end, check_out_time, all nullable time(0) without time zone, restricted to 00:00:00<=clock<24:00:00. Zero is a real midnight; null is unknown. check_in_window_end_day_offset smallint defaults0 and is limited 0/1. A window end requires a check-in; absent end requires offset 0; an offset 0 end must be>=check-in. An offset 1 end must be<check-in, representing one overnight window under 24h. time_zone text is nullable; any supplied value must be an accepted named IANA zone through the existing validated-zone helper. These local planning clocks do not silently create confirmed instants.
3. Stay personal notes text nullable, bounded to 20,000 UTF-8 bytes; created_by_person_id required, deleted_by_person_id nullable, both composite family FKs to people(id,family_id); created_at/updated_at timestamptz required; revision bigint positive default 1, advanced server-side on every material stay/link change; deleted_at timestamptz nullable with the existing paired-delete-actor invariant. Add unique(id,trip_id) for scoped associations. Tenant/family_id redundancy is deliberate and enforced by composite FKs, matching existing saved-location integrity. Owner IDs are never client-asserted authorization.
4. **public.trip_stay_booking_links**: reservation_id uuid PK, stay_id uuid unique, trip_id uuid required; composite FKs(reservation_id,trip_id) to existing trip_reservations(id,trip_id), (stay_id,trip_id) to trip_stays(id,trip_id), all ON DELETE RESTRICT. This is optional 1:1 for the current native partner-booking contract, not a unique hotel/Trip constraint. Repeated bookings/stays remain separate records. Future many-booking stays would be an explicit cardinality change; do not invent primary-booking selection now. Transactional guards require a hotel booking and active same-Trip stay/location, reject link/type changes inconsistent with that rule, and increment the affected stay revision. Link/unlink has reversible before/after receipts; it does not delete either content record.
5. Add **timing_kind text** and **time_zone text** to trip_reservations, rather than a second independently editable copy of starts_at/ends_at. Kind is untimed/timed/legacy_unclassified. Untimed requires both instants null and zone null; timed requires at least one finite existing instant and a valid named zone; unclassified retains existing instants unchanged with zone null. New columns are staged nullable, all original rows remain NULL/unclassified without any UPDATE; defaults classify only new inserts. Original instants remain unchanged. Never infer unknown timing from00:00. Transport timing stays endpoint-specific; leave its header timing unclassified and its new header zone null until a separate endpoint-aware command is qualified. Cross-table/legacy-write guards must prevent old writers from silently changing classified timing; exact unchanged legacy text writes remain compatible.

All exposed tables enable RLS. Revoke default PUBLIC/anon/service/client writes. Reads use original Family membership, AAL and active Trip/location/stay rules, with both direct SELECT and RPC negative tests. Internal history/receipts live in family_auth with no client table grants; security-definer entry points have fixed empty search_path, schema-qualified names, explicit current-user/AAL/Trip authorization and only authenticated EXECUTE. Do not use user_metadata for authorization. Reuse actual existing helpers and evaluate proposed indexes with EXPLAIN on fixtures; do not weaken existing policies or grant table administration to make tests pass.

Required indexes: stays(trip_id,arrival_date,id) WHERE deleted_at IS NULL; stays(location_id,trip_id); stays(family_id) and each actor FK as needed beyond existing leading indexes; a partial trash listing index(trip_id,deleted_at,id); link(trip_id,reservation_id), plus the unique stay index already covering reverse lookup. Avoid duplicate indexes already supplied by PK/unique constraints. No partitioning/materialized view is justified at this scale.

## Commands, reads and transaction boundaries

Use the qualified stay-only original scope {version:1,trip_id,family_id,user_id,person_id,session_id,layer:'published'}, operation_id uuid and canonical observed revisions/records. Context/history RPCs and acknowledgement-only results are specified in the B2b2 actual handoff; older six-field contracts remain unchanged. Do not add writable native numeric IDs to SQL; the adapter translates to existing UUID namespaces. Reads bind source/user/Family/person/Trip/revisions, exact row identities and bounded arrays. Stable-snapshot reads must include booking/stay/location/date facts from one transaction, not unrelated caches.

Target interfaces, each returning a versioned bounded JSON object:

- get_family_trip_stay_view_v1(p_trip_id uuid): complete active stays, qualified same-Trip links, location identities, civil-day associations, revisions and a named completeness state. A real unavailable contract is an error, never a successful empty list. An off-calendar stay remains in canonical output even though a native consumer requiring two day IDs cannot yet display it.
- get_family_stay_editor_v1(p_trip_id uuid,p_stay_id uuid): exact stay/link observation, original capabilities and any admission refusal.
- save_family_stay_v1(p_trip_id uuid,p_stay_id uuid,p_operation_id uuid,p_scope jsonb,p_observation jsonb,p_changes jsonb): strict-whitelist patch or explicit create with client-generated stay UUID. Omitted fields remain unchanged; null explicitly clears only nullable facts. Repeated intentional creates use new operation/entity UUIDs; retrying one operation reuses the exact request digest/result. No arbitrary metadata/time-zone replacement.
- set_family_stay_booking_link_v1(p_trip_id uuid,p_stay_id uuid,p_operation_id uuid,p_scope jsonb,p_observation jsonb,p_reservation_id uuid): null unlinks, otherwise links exact hotel booking. Enforce the optional 1:1 relationship and original revision atomically.
- trash_family_stay_v1 and restore_family_stay_v1 use the same trip/stay/operation/scope/observation signature as Save, without a changes argument. Their receipts preserve linked records and private notes. Restore refuses a foreign/deleted location or inconsistent link rather than silently relinking/recreating content.
- save_family_booking_timing_v1(p_trip_id uuid,p_reservation_id uuid,p_operation_id uuid,p_scope jsonb,p_observation jsonb,p_timing jsonb): later separate command. p_timing is an exact untimed or timed object with explicit basis and named zone; local basis requires explicit offset disambiguation where needed. Preserve both original instant and named zone, reject nonexistent local times, and verify overnight dates. No timing activation in the first foundation packet.

Stay-only commands require current Direct trip.schedule.manage; changing a booking/link additionally requires Direct trip.reservations.manage. Creating a native partner booking/stop is one explicitly declared combined command and must check every affected permission before writing anything. Propose-only actors receive the existing truthful refusal until typed proposals exist; no published fallback or partial save. Do not infer confirmed status merely from a nonempty code.

Reuse the existing trip-recovery advisory lock and established Trip row lock before sorted child locks. Reauthorize after locking, compare observations, validate all references, write content/history/receipts together, and return canonical result/revision. Receipt retries reauthorize and compare request digest; an old acknowledgement is never a fresh replacement record. Reuse deterministic PT409 conflicts and existing permission/unsupported error conventions. Do not perform network/Storage deletion inside transactions.

## Recovery, media and compatibility

Parent Trip Trash hides stays/links without physical child deletion. Stay Trash retains the link and booking; deleting a booking must not implicitly delete the planned stay, location, shared hotel, files or independent Journey history. Add stay/link ownership to the actual aggregate export/restore/purge inventory and test it; do not assume generic soft-delete columns provide aggregate recovery. Normal clients cannot purge. A later explicit retention purge must account for restrictive FKs and append-only receipts/audits. Link removal changes only an association and has reversible command history.

No new media copying: use existing saved-location/catalog object identities and ready variants. File/media links and retention holds keep their original sources. Neither native cascade deletion nor transformation fallback is adopted.

Existing iOS implementation is not a feature gate. Shared database writers are still relevant: additive columns and explicitly guarded old writes preserve their legitimate text/date behavior; any conflicting old clock/link writer is denied/versioned until compatible. Do not maintain two editable timing stores or silently redirect legacy metadata to the new authoritative facts.
