## Purpose and boundaries

A complete offline Trip is one explicitly scoped, checked local read model for the supported native Trip workspace. It is not a database backup, a copy of the whole Family account, an authentication session, a write grant, a queue receipt, or a promise that provider maps and every original photo/file are downloaded. The complete TREK 5.1.2 source merge is present; the declared upstream pin remains 5.0.1 until the remaining acceptance gates pass.

Preserve canonical UUIDs, the saved-location/visit distinction, repeated visits, explicit untimed versus genuine midnight appointments, named zones, booking precision, private data and existing Family direct/propose/deny rules. Preserve the native desktop/phone layouts. Catalog displays and prefetch use stored `variants/v1` objects or placeholders, with no automatic original or `/render/image/` fallback. No hosted schema, billing, provider settings or production migration is needed for the cache contract or first repair.

## Admission model

There are three distinct modes:

1. **Online current access:** fresh server-validated identity, Family membership/assurance, Trip access and normal guarded readers. Existing RLS/RPC rules remain authoritative for reads/writes.
2. **Last-authorized offline read:** a future explicitly qualified, complete local snapshot may display the data this same device/account was previously allowed to download, within its freshness policy. It cannot discover a remote revocation while disconnected. It must clearly remain read-only and become unavailable after known local revocation/logout/expiry. This mode is not implemented or enabled by D13.
3. **Retained original work recovery:** exact original queued commands/attachments remain owned, paused and losslessly exportable. A historical acknowledgement, display identity or exported file does not resolve or authorize them. Every receipt lookup or retry keeps original scope/body/operation UUID/revision and current permission/MFA checks.

Supabase `getSession()` loads attached storage. Its presence alone cannot establish current Family access. SDK `getUser()`/server validation and the Family access gate remain required for online authority; no token is copied into a snapshot. Offline display evidence is deliberately different from a current authorization claim. Official references: [getSession](https://supabase.com/docs/reference/javascript/auth-getsession), [getUser](https://supabase.com/docs/reference/javascript/auth-getuser). Changelog reviewed for this packet; no SDK or stack upgrade is required or performed.

## Version-one envelope: required shape

Use a new explicit format, `family.offline-trip.v1`; never relabel or silently upgrade the partial v1 planner cache or an unqualified native bundle as complete. All field names below are proposed contract names, not existing database columns or an already implemented parser.

- `format`: exactly `family.offline-trip.v1`.
- `generation_id`: newly generated UUID for this immutable complete snapshot.
- `owner_generation_id`: persisted local ownership generation, distinct from the snapshot generation and the in-memory private-session epoch. Logout/revocation retires it. An identical source/account returning later obtains a new generation; equality of UUIDs, payloads or timestamps cannot resurrect an old generation.
- `trip_generation_id`: the persisted per-Trip barrier generation under that owner. Capture/read/write/publication must reject a changed Trip barrier even when its previous snapshot was absent and source/account IDs are identical. It is separate from the canonical SQL Trip revision.
- `scope`: `{source, data_plane, user_id, person_id, family_id, trip_id, planner_layer}`. Canonical UUIDs only; source is the configured normalized project origin (trimmed, no credentials/query/fragment, trailing slash removed). Explicit `data_plane: supabase`. Support only `published` for initial complete offline admission; `myDraft` remains unavailable for cold reads until its complete companion composition is separately qualified. It must never fall back to published under the same request.
- `identity`: `{scheme: family-trek-view-identities-v1, registry_scope_user_id, bindings}` where every binding is `{kind, uuid, key}`. Registry owner equals scope user; keys must recompute and be unique using the existing registry algorithm. Required references must resolve. Outer source/actor/Family/Trip/layer and generation checks apply even if deterministic numeric aliases match across projects.
- `capture`: `{started_at, completed_at, last_verified_at, expires_at, policy_version, producer_commit}`. UTC timestamps, ordered/finite, and a known policy version; future times/clock rollback cannot extend validity. A local hash or timestamp is corruption detection, not a cryptographic access grant. No JWT, refresh token, password, MFA secret, cookie, service-role key or signed Storage URL is allowed.
- `components`: all required component envelopes below, each with its own version, explicit origin scope, captured revision evidence, item count, canonical payload and integrity digest. Empty success is represented by a validated empty payload/count zero; absence, refusal, truncation and unavailable are distinct and never become empty success.
- `capabilities`: supported read surfaces only, tied to the producer contract. Excluded/disabled Tours, Collab, driving preferences and other unsupported features stay disabled. No cached direct/propose permission is a live grant. Writes/replay remain controlled by the existing command system.
- `media`: bounded manifest of available optional catalog variants and private originals, separately qualified by the complete source/actor/Family/Trip/file/media identity and byte-integrity metadata. A URL alone is not a downloaded file.

Strictly validate known versions, safe counters/integers, bounded strings/arrays/JSON, real dates/zones, unique IDs and all cross-links. Initial maximum JSON envelope is **16 MiB**, consistent with the current online bundle bound, with existing stricter per-component limits retained (including planner/booking 8 MiB and task/packing 2,000 active records). This is a rejection boundary, not permission to drop overflowing rows. The initial packet must refuse an oversized/incomplete download honestly; pagination requires its own consistent completion marker before supporting larger Trips. Byte bodies stay outside JSON with separate bounded quota accounting.

## Required components and revision evidence

Every component below is required for a complete supported Trip workspace, even when its valid collection is empty. A read refusal cannot be downgraded to an optional section. Optional media bodies and explicitly disabled features do not change complete-data status.

### Header, planner and identity

Retain the canonical Trip header, Family owner and supported dates/configuration, the full checked `PlannerView` and variant descriptors, and the identity binding manifest. Keep saved-location IDs separate from catalog source IDs and visit IDs. Do not serialize projected numeric IDs as canonical locations. Preserve full visit timing fields, `timing_kind`, day IDs, zones, repeated occurrences and catalog description versus personal/location/visit notes.

Header dates and the planner/booking day spine must agree under the existing calendar validation. If the header has no revision token, record that honestly as bounded capture-time data; do not invent one or call it a transactionally consistent global snapshot.

### Tasks

Keep the complete validated `TaskList`: version, scope, `trip_lifecycle_revision`, collection revision, original row revisions, canonical tasks and Trash count. Task scope is published and actor-qualified. Native task aliases are derived from this packet. A zero task list must be a successful authorized read. Trash history itself is not silently prefetched or fabricated from the count.

### Packing

Keep the complete validated `PackingList`: scope/lifecycle/collection revision, item row revisions, bags, member/owner/recipient/contributor associations, category assignees, unassigned/server-summed bag weights and Trash count. Preserve private actor filtering. Reconstructing weights, visibility or bag membership from projected item rows alone is insufficient. Native packing authoring remains gated independently.

### Bookings and transport details

Keep the complete validated `PlannerBookingView` before projection: canonical records, original metadata, confirmation/status, day/date state, endpoints, legs and visit association. Preserve microseconds and IANA zones; do not round-trip canonical clocks through native minute-only widgets. Keep `trip_revision` and the exact canonical day spine, and run `assertBookingCalendar` against the same planner packet. Unsupported hotel stay clocks and other writers remain unavailable.

### Budget, files, members, categories and tags

Retain the current authorized read payloads with their declared actual canonical/source identities and checked links. Existing handlers may expose some of these as compatibility projections; those projections are not promoted to canonical commands or fabricated revision tokens. Add explicit reversible ID bindings for every supported linked item, including assignment/location/file/reservation/member references. Reject ambiguous or foreign references. Current expense/cost writers remain independently gated.

Files require metadata/link identities even if their bodies are not downloaded. Private bytes are optional but separately gated: an absent byte is unavailable offline, not a failed original request replaced by a public URL. Membership display data is not fresh Family permission. Categories/tags must remain scoped to the same source/Family; family-wide definitions are declared as such rather than mislabelled Trip-owned.

### Compatibility revision vector

The envelope records a vector: planner Trip revision/draft evidence; task and packing lifecycle plus collection/row revisions; booking Trip/calendar revision; and explicit capture/check evidence for resources lacking versioned reads. Match overlapping lifecycle/calendar/link evidence before commit. Independent reads cannot promise one global MVCC instant. If task and packing lifecycle revisions disagree, or referenced days/locations/visits are incompatible, reject/retry the complete capture rather than merge it.

Unversioned mutable resources remain capture-time copies. If a stronger cross-resource guarantee becomes necessary, design a dedicated read RPC after measuring need; do not add a hosted schema migration merely to fabricate a cache token. Do not tie task/packing published scope to a private itinerary draft without an explicit, tested compatibility declaration.

## Atomic capture and publication

1. Require the actual current online Family validation and a live source/actor/person/Family/Trip/layer/private-session owner. Obtain the existing guarded original-work/read lease and compare the native optimistic state fingerprint. No arbitrary cached identity may start a complete capture.
2. Collect all required canonical packets and compatibility resources under that owner. Keep network/RPC waits outside IndexedDB transactions. After each await, verify the original context/abort/Trip invalidation/layer and identity registry remain current.
3. Validate each packet and every cross-link/revision/calendar/privacy rule; build the complete native projection in memory. Refuse missing/failed/oversized components as one failed capture. Do not set a download-success indicator from a partial subset.
4. Commit the immutable envelope and active pointer in **one** transaction in the dedicated Family snapshot database after rechecking original owner generation and guarded local-work state. Hashes/counts and the pointer must refer to that same generation. Do not distribute an alleged atomic commit across independent Dexie databases.
5. A quota/crash/abort/late body leaves either the previous valid complete generation or no complete generation. A known revocation invalidates the previous generation regardless of capture failure. Compare-and-delete/replace must not remove a newer accepted generation.
6. Any later individual task/packing/booking/file read must not silently patch an active complete generation. It can stay in memory or request a new complete capture. Stale components never produce a new `completed_at` or extended expiry.

## Cold read and pending work

A future cold reader must validate the entire envelope/identity manifest and current **local** owner-generation record before mounting supported Trip views. It must select exactly one complete generation. Never combine an old cached header with newly projected task/booking/packing companions. Malformed/future-format/expired/foreign/tombstoned/incomplete data produces owned recovery, without privileged HTTP requests or a write grant.

Version one retains the existing **15-minute** freshness limit; reads cannot extend it. This deliberately introduces no silent multi-day offline retention. A later explicit native per-Trip download policy may extend retention for travel after consent, device privacy and expiry behavior are specified/tested. Until that later packet passes, the product must not claim that whole Trips remain available throughout a multi-day vacation. Browser eviction can always remove local data; a cache is not an independent backup.

When affecting original queued work or protected local edits exist, preserve the current recovery barrier. Do not hydrate/replace the workspace over those originals, replay on open, repair IDs, change layers, adopt a new revision/body, discard import files or silently clear work. Export of an unsupported original stays lossless and unresolved. Current receipt/retry checks require online authority; a snapshot cannot resolve them. The future offline read mode must not enable native optimistic writes that do not use qualified commands.

## Retirement and device data

D14 qualifies this lifecycle for known partial snapshots. D15 must extend the same retirement to every new complete-envelope/pointer store before writing it; cold admission remains gated.

- Stop/invalidate the retired owner synchronously, then retire its disposable snapshot generations on completed logout, known membership/Trip-access refusal, actor/person/Family/source replacement and cross-tab private-session retirement. Trip deletion/Trash/invalidation must not expose an older generation as current. A transient network outage is not a membership refusal.
- Startup must classify the existing legacy partial rows; unqualified prior-owner data is disposable, never automatically adopted as a complete snapshot. Unknown/future cache formats stay inaccessible and cannot trigger a database-wide deletion that risks protected commands.
- Generation ownership must survive same-account ABA. An old late write/cleanup must neither resurrect old rows nor delete a fresh same-account generation, even with equal content and a frozen millisecond clock. A shared persisted ownership/tombstone record and same-database atomic conditional writes are recommended over timestamp-only comparisons. Cross-tab observers must fail closed if invalidation/ownership storage cannot be read reliably.
- Retirement touches only known disposable read data and derived/private media belonging to the retired owner. It does not clear static app assets, unrelated source/account caches, original mutation queues, pending uploads, retained recovery exports or backups. The existing `api-data`/`user-uploads` cleanup is separate and must remain intact.
- A denied/quota/unavailable IndexedDB cleanup must not block logout or reactivate the old owner. Record/report incomplete local erasure; subsequent cache reads remain unavailable until safe revalidation/cleanup. Do not describe failed deletion as successful erasure.
- Plain browser cache data is readable by local device access/devtools and same-origin code. SHA-256 is integrity checking, not encryption. This packet adds no at-rest encryption promise or key store. Sensitive downloaded bytes need deliberate device-retention policy; never store privileged credentials alongside them.
