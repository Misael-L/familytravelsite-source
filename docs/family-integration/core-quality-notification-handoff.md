# Q71 — terminal inbox pagination repair

Completed locally 17 November 2026. A demonstrated paging bug took priority over the proposed complexity refactor: positive offsets at or beyond a terminal cursor could restart page one and return duplicates. They now return an empty native inbox envelope.

## Demonstration and exact repair

The original exported handler reproduced this with a valid one-row/nextCursor-null fixture in direct and actual request-scoped execution. A cached terminal offset1 issued another list; an uncached offset5 walked to the end then listed again. Both returned the first row again. This was a paging/redundant-read bug, not evidence that the original context-retirement fence admitted a stale result.

The only runtime change is five inserted lines in `client/src/integrations/family/notificationHandler.ts`. After the original cursor walk and before the final list call, `offset > 0 && cursor === null` awaits the existing scoped unread count, stores terminal null only after success and returns `notifications: []`, `total: offset`, that unread count and `has_more: false`. Exactly the redundant list is removed on this path. Offset zero still reads page one, and nonterminal requests still execute the original code. The existing total-as-loaded-extent convention is preserved; no new database count or inference is introduced.

Every original runtime statement/import/Cursor/WeakMap/projection/query/scoped operation/mutation remains exact. No new runtime helper, import/export, cast, default, API or async wrapper. The unused pre-repair refactor proposal stays private in `/private/tmp/trek-core-quality-notification-source-20261117/refactor-proposal`; it was never applied and is not qualified for the repaired source. Its former complexity measurement must not be reused after this fix.
