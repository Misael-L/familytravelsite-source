# Integration preview cutover and fallback

The website source can recover scoped task and packing saves on schema 155. Production and integration preview still run releases that call the direct table writers and legacy packing RPCs. Schema 155 refuses those operations. Promotion therefore needs an ordered database and website cutover across every client that uses the target project. A preview-only Worker change offers no protection to older tabs that send requests straight to Supabase. [Observed hosted versions](supported-core-readiness/recheck-20261121-schema154/hosted-postgres1712-and-worker-binding.json)

## Local rehearsal

The rehearsal used the encrypted X8 database snapshot in a disposable PostgreSQL 17.12 container. GoTrue and PostgREST shared the container's isolated loopback. The authenticated requests came from synthetic Family members with real password and TOTP sessions. All 200 archived projections and all 296,764 original rows matched after applying the 67 pinned migrations.

The write pause was a PostgREST pre-request hook in a private test schema. It read one durable, fail-closed state row. Read-only transactions could continue with ordinary permissions. Each potential write acquired a shared transaction lock before inspecting the state. Non-read-committed writes and missing state failed closed. The fixture granted read and execute access to the hook and state, and only the operator could change the state. A pending REST update held its shared lock after it reached the API. Closing the gate refused new writes, allowed the existing update to finish once, and let the operator verify that the old transaction had drained by acquiring the matching exclusive lock.

The pause remained closed during the migration replay. On schema 155 the task and packing readers and their receipt lookups still worked. The test opened the gate and confirmed all nine legacy paths returned insufficient privilege. Both replacement commands succeeded. Re-closing the pause preserved access to their committed receipts under the original Family. A different Family could not read those receipts. Reopening let the original commands return their prior results, and SQL confirmed one record and one receipt per operation. [Scoped rehearsal results](supported-core-readiness/recheck-20261121-schema154/preview-write-pause-and-fallback.json)

The source-bound fixture build showed both sets of saved rows with writes paused. After reopening, a signed-in desktop Chromium session saved a task and a packing item through the replacement APIs. A later save during the pause stayed in IndexedDB with its original operation ID, target and payload. Independent SQL found no record or receipt for that paused save. This build used loopback and the isolated writer profile.

## Hosted route and migration preflight

The active production and preview entry points load the same primary Supabase client configuration. Their bundle hashes match the recorded Worker releases. Supabase returned no development branches for this project. Treat the current preview as a production database client and include it in the cutover scope. [Observed sources and backend](supported-core-readiness/recheck-20261121-schema154/hosted-route-coverage-and-role-replay.json)

The project is on PostgreSQL 17.12 and still has 88 applied migrations. The hosted catalog shows no stored pre-request setting in the inspected scopes. The non-superuser `postgres` login has admin rights on `authenticator` but no explicit SET grant for the pre-request parameter. The database-scoped hook setting failed with insufficient privilege in the modeled local login. Hosted hook installation and propagation remain unverified.

One active Cron job calls the Family export dispatcher. The storage cleanup schedule was inactive, and 11 deployed Edge Functions were active. The shared backend source shows the export dispatcher creates and removes Storage objects as well as processing jobs through database RPCs. Stopping a scheduler alone cannot drain outstanding requests or prevent explicitly triggered invocations. Account for that job, uploads and already-issued upload authorizations, other privileged Edge Function calls, direct SQL clients and any in-flight Auth or GraphQL work. Realtime publication and Storage policy inventory do not prove quiescence. [Hosted write-route evidence](supported-core-readiness/recheck-20261121-schema154/hosted-route-coverage-and-role-replay.json)

The exact isolated 17.12 image loaded Supautils 4.0.0 with the hosted policy delegation. This resolved the earlier local-only ownership refusal on `storage.objects` without changing ownership or elevating the migration role. The restored non-superuser `postgres` then applied 40 pinned migrations. Migration `20261112235203` stopped at the platform-admin defaults and rolled back. The hosted catalog confirms that `postgres` cannot assume `supabase_admin`. It also shows eight of the targeted table defaults under that protected role. The separate earlier rehearsal using elevated local privileges remains valid for SQL and data preservation. This captured the original pending migration before the managed-role reconciliation below. The revised migration verifies existing application table ownership in `public` and `family_auth`, removes the same client table rights, and manages the defaults of the app's `postgres` owner. The platform role's defaults still apply to tables it creates. Keep application table creation in the `postgres` migration path and check the application-owner contract if that changes.

All 67 migrations passed under the modeled non-superuser login with Supautils 4.0.0 and the observed policy delegation. Two newly created application tables confirmed the expected effective defaults. ## Layered write pause rehearsal

The modeled non-superuser `postgres` role changed a disposable Cron schedule, removed fresh export admission and installed temporary restrictive Storage policies. With the exception of the local service stop, these controls used the same database role attributes and Storage policy delegation observed on the target. All 296,764 original rows survived. [Isolated receipt](supported-core-readiness/recheck-20261121-schema154/managed-write-pause-layers.json)

- **Exports.** The test first disabled the synthetic schedule and revoked service execution of the claim and expiry RPCs. A new call to either returned insufficient privilege. An already-claimed job could still upload its bytes and record completion. Both grants and the schedule were restored. Deletion work that already completed the expiry RPC can still be running outside the job's processing state. Check dispatcher/Storage completion and outstanding scheduled HTTP work alongside the processing count.
- **Storage.** The local Storage API refused fresh uploads, overwrites and new signed upload authorizations. An attempted delete returned HTTP 200 and retained the original bytes. A signed upload authorization issued before the pause still wrote a file, as did the trusted service role. The packaged API needed a local compatibility index on the disposable versioned metadata copy to exercise writes. Hosted behavior, multipart, resumable uploads and any other signed route require their own checks.
- **REST and direct SQL.** Stopping the local PostgREST service made its reads and writes unavailable. Restart restored the selected read. Auth, Storage and direct SQL continued to respond during the stop. A direct SQL writer committed once. A scoped lock probe detected its in-flight transaction and succeeded after the commit. The lock probe measures drain at that instant. Continuing admission needs separate controls for the actual import and maintenance clients.

For a hosted window, first stop new work on the affected origins and across privileged entry points. Close export admission and disable the matching active schedule while the completion RPC can still operate. Confirm that prior export uploads, deletions and pending HTTP invocations have finished. Stop issuance of upload authorizations and establish that existing authorizations and active transfers have expired or drained. Pause trusted Storage/Edge callers and external SQL writers independently.

Only after that drain should a proposed Data API suspension occur. Confirm REST and GraphQL behavior independently where exposed. Keep the download/export route for retained browser drafts available ahead of the outage. Restore REST and validate the schema-compatible website before reopening the write paths. Resume the export schedule after its endpoint, permissions and Storage flow pass. Verify the hosted settings switch, propagation and reversal procedure at the start of the authorized production window. An unproved pause stops the migration. [Rollout order](core-release-prerequisites.md#order-from-here)

## Detached browser draft recovery

The normal Offline settings export reads the active account database. Older unmarked databases require the standalone device recovery utility. The tested legacy preview schema is IndexedDB version 140. A Family sign-in, a matching numeric suffix and access to a newer account database do not establish ownership of older work.

The public production and preview service-worker bytes matched the recorded releases. In Chromium, each worker served its cached app shell for the recovery URL. A normal update to the generated recovery-qualified worker reached the exact standalone document on the same origin. The browser used an inert app shell to isolate the worker transition and synthetic databases for the drafts. Desktop and phone-width runs preserved the selected draft, original import key and file bytes. The utility refused an owned legacy database and a future schema, excluded a different origin and the current account database, and made zero dynamic API requests. The ordinary control build emits neither the recovery page nor its export code. [Browser evidence](supported-core-readiness/recheck-20261121-schema154/detached-browser-draft-recovery.json)

Before a hosted recovery action:

1. Match the original browser profile and website origin. Preview and production have separate browser databases even when they use one Supabase project.
2. Verify an authorized, standalone recovery artifact on the original origin and a worker that routes to it. A successful HTTP fetch by itself does not verify the page shown to an already-controlled browser. Confirm the recovery document before accepting consent. Preserve the existing IndexedDB stores and queue.
3. Select one compatible database explicitly. Keep the checksummed local archive private and preserve the original browser data. The archive carries no trusted Family account or source and has no replay path.
4. Compare a known scoped operation with its receipt when the original identity can be established independently. For unscoped work, verify the correct account and Trip separately and compare the archived contents with the saved state. Keep uncertain entries for review until ownership and the saved outcome are established.

The updated fallback was also replayed at the exact production and preview HTTPS hostnames with local DNS and a test certificate. It accepts those two origins and refuses recovery on an unrelated origin. Hosted delivery and checks in any affected real browser profile remain part of cutover acceptance.

## Before scheduling hosted work

1. Pin the selected production and fallback artifacts to their exact HTTPS origins, Supabase target and corresponding source. Qualify their behavior locally against schema 155. Include both deployed Workers in the transition because they share the same project.
2. Inventory the effective pre-request configuration and API topology. Preserve existing hook behavior. Specify how the operator will confirm the pause and drain across the managed API instances and restore service if that check fails. Run the hosted confirmation in the approved window before the first migration. The local fixture exercised one PostgREST process and its connection pool.
3. Account separately for direct database sessions, service jobs, Edge Functions, GraphQL, Storage and Auth writes that could affect the migration. The local fence covers PostgREST transactions. Its test says nothing about enforcement by another gateway or about work already outside PostgREST. Coordinate the related write routes before calling the shared project quiescent.
4. Capture and verify the pre-cutover database, migration ledger and required media worklist against the X8 backup. Schedule a write pause with an explicit scope, stop condition and owner for closing and reopening it. Any earlier backup is evidence for recovery, while freshness is assessed for the chosen window.
5. Preserve pending work in each affected browser profile and origin. Check the receipt before retrying a scoped command, using the same operation ID and payload. Export already-owned legacy drafts for manual comparison with saved records. Use the rehearsed standalone path for compatible detached drafts once its hosted delivery is qualified on the affected origin. Complete the draft capture and review before directing users to reload for the planner cutover. Keep raw drafts and unresolved data separate from publication artifacts. Never clear browser storage as a cutover step. [Prior browser handover](core-release-prerequisites.md#g3-different-release-handover)
6. Use the pinned preview and production writers and the updated schema 155 fallback with its recovery entry. Each needs a source receipt and the correct schema and capability contract. The two Workers currently serving traffic cannot save tasks or packing through schema 155.

## Maintenance window and conditional approval

Upload the fallback with `wrangler.recovery.jsonc`. Cloudflare's default HTML handling redirects the recovery page to its extensionless alias. The generated service worker exempts the explicit `/device-work-recovery.html` pathname from SPA routing. The recovery configuration serves that path directly. Before routing either live Worker, check that the version serves HTTP 200 with the pinned HTML bytes and no redirect. [Cloudflare HTML handling](https://developers.cloudflare.com/workers/static-assets/routing/advanced/html-handling/)

Approval covers one maintenance window and the 67 pinned SQL files, from `20261104175741` through `20261121184611` at backend commit `c14ba0a8c`. The SQL bytes match the rehearsal. The live read-only check still shows PostgreSQL 17.12 and 88 applied migrations. [Ordered migration list](supported-core-readiness/recheck-20261121-schema154/managed-role-migration-replay.json)

1. **Before changing service.** Confirm the live migration ledger and exact pending hashes against the rehearsal. Record both active Worker versions, the original Data API setting, export scheduling and admissions, and the owner who can restore each control. Bind the checked build receipts to the proposed Worker versions on their exact origins. Keep the old versions available for the case where the migration never starts.
2. **Preserve browser work.** Deliver the authorized fallback and recovery page on both original origins as planned for the window. Confirm the currently controlling service worker delivers the standalone document in each affected browser profile. Export any required work before directing users to reload into the candidate. Keep the original databases and any private exports. Stop if a needed export or origin check fails.
3. **Pause and drain writers.** Stop new site and privileged write admission. Close export intake, let existing jobs and transfers finish, and stop issuance of new signed uploads. Account for outstanding signed authorizations, background functions, direct SQL and scheduled HTTP jobs. In the Supabase Dashboard, open the Data API integration overview and turn **Enable Data API** off during the approved window. Compare previously successful authenticated read probes against REST and exposed GraphQL after propagation. Confirm old transactions have drained. A failing unauthenticated request alone is insufficient. If any required path remains open or drain cannot be proved, stop before the first migration.
4. **Capture the recovery point.** With writes drained, take a fresh incremental generation using the existing X8 generation for reuse. Verify the new database dump, object manifest and media bytes on the encrypted X8. For any initial transfer, run the existing incremental tool in Terminal and use a new sibling generation directory. Resume an interrupted run with that same directory. Check that the confirmed snapshot is the one taken during the pause. Stop if verification fails. The 20 November generation remains the previously rehearsed recovery point.
5. **Apply and validate.** Apply only the approved migration set in order. Keep normal editing paused while re-enabling the necessary read and controlled test access. Confirm replacements and privilege checks, then use the restricted Cloudflare preview and a designated test trip to check saves, reads after reload, receipt reconciliation and retained work. Reopen ordinary traffic only after those checks and the production version pass. If writers cannot remain controlled during acceptance, stop before starting the migration.

If the window stops before the first migration, verify that the original ledger is intact, reverse the recorded controls and restore the original Worker versions as needed. If any migration has committed, use the checkpoint and fallback rules below before restoring normal writes.

## Cutover decisions

- **Before the first migration.** If any fence, preservation or fallback check fails, stop the schema change. Reopen legacy writes only after confirming the old ledger and the original access rules. Reconcile any failed sends and in-flight receipts first.
- **During the migration.** First prove the pause across affected clients and the drain of old writers. Apply the pinned set in order. Record the exact ledger at each failure point. Treat any committed prefix as a database state requiring its own recovery decision. A failed migration does not undo any earlier committed version.
- **After the new schema is active.** Keep the pause on if the replacement fails. Use the separately qualified recovery artifact for readable state, original receipts and export where supported. Keep old direct writers out of service even if the website version is rolled back. Resume writes with a qualified schema 155 writer only after pending work is reconciled and the selected signed-in flows pass. If restoring the database is required, apply the separate database-and-media recovery procedure against a verified restore point and account for commits after that point.

The rehearsal does not install a hosted pause, bind a Worker version, publish source or approve a migration window.
