# Family Collections v1 — recovery, location content and transfer contract

Status: recovery, normalized storage/history, bounded reads and observed item authoring are qualified locally at schema141. See [C4 authoring acceptance](collection-content-authoring-handoff.md), [exact command contract](collection-content-authoring-contract.md) and [next native reader/writer/queue/recovery cohort](collection-native-authoring-packet.md). Root authoring, transfers, sharing and private byte activation remain separate. No hosted migration or native activation occurred. Four transfer refusals and item-removal containment remain; no transfer success is inferred from this foundation.

## 1. Evidence and architectural choice

The new isolated schema136 copy contains three lists and one item; those are **local frozen-copy counts, not a current production inventory**. All nine rollback-only probes demonstrate their stated conditions: physical old-API removal, catalog/root cascade loss, unique-violation retry behavior, no manual kind, missing live-session enforcement in the legacy edit check, plus existing exact-one-target and kind/target constraints. The authenticated-role probes simulate trusted decoded claims; they do not prove a new signed-token/GoTrue path. No original record is used as a mutation target. All362,455 baseline rows across242 COPY projections survive; no synthetic row remains.

**Decision: extend `lists` / `list_items`, with one optional location-content child.** Do not introduce a second Collections library, a generic unconstrained entity UUID, a new geography hierarchy or a Trip/reservation table. The existing eight catalog FKs already enforce real entity identity. Keep them. Add an explicit manual item kind in a separately committed enum migration, followed by the location-content migration; PostgreSQL cannot use a newly added enum label in the transaction that adds it. Never overload `place` with an absent city FK to represent a restaurant or manual point.

A new saved location is an independent **typed content snapshot**, not a live alias of a Trip. Keep its display name/notes/status/order on the existing item and its spatial/details/media content on a one-to-one child. Preserve the catalog source FK for identity/deduplication, but later catalog edits must not silently rewrite kept personal content. A link-only legacy item remains link-only until an explicit observed materialization; do not synthesize historical snapshots or bulk-backfill content. A raw JSON copy of a native request is not the live relational model. Versioned JSON is permitted for validated committed-state history.

This child relation is preferable to adding location-only columns to every country/airline/guide item. It avoids duplicating source identity while retaining existing list/item IDs, ordering, status and notes. Shared catalog description, saved-item notes and scheduled-visit notes remain separate facts.

## 2. Storage contract and invariants

### 2.1 Recovery foundation, before new manual/location content

Add to **both** `public.lists` and `public.list_items`:

- `revision bigint NOT NULL DEFAULT 1 CHECK (revision > 0)`, server-managed, incremented once for a changed committed-state transaction; a deliberate no-op does not increment.
- `recovery_xid xid8 NULL` with no volatile default, solely to coalesce multiple physical edits of that row in one transaction. Do not expose it through native/history projections.
- `deleted_at timestamptz NULL`, finite when present.
- `deleted_by_user_id uuid NULL REFERENCES auth.users(id) ON DELETE RESTRICT`, with `(deleted_at IS NULL) = (deleted_by_user_id IS NULL)`. This records an authenticated global administrator without inventing a Family-person identity. It is not returned in normal public projections.

Add to `public.lists`:

- `lifecycle_revision bigint NOT NULL DEFAULT 0 CHECK (lifecycle_revision >= 0)`, incremented for Trash/Restore and archive/unarchive transitions, separately from content revisions.
- Unique `(id,family_id)` for future scoped children. Root ID/family/creation identity remain immutable.

Add unique `(id,list_id)` to `public.list_items`; item ID/list/source kind/eight target FKs remain immutable. Root/list and item revisions are not client write fields. Existing `archived_at` is **Archive**, not Trash: root Trash retains its archive state, children and item tombstones; Restore does not unarchive it or restore independently trashed items. An archived root must be unarchived before child mutation. Permanent DELETE and TRUNCATE of protected roots/items/history are refused for every application/service role; no purge/automatic retention job is introduced.

Use `family_auth.collection_state(list_id uuid PRIMARY KEY REFERENCES lists(id) ON DELETE RESTRICT, content_revision bigint NOT NULL CHECK(content_revision > 0))`. Missing state means revision0 for an unchanged legacy list. Insert/update of an item advances the content revision under the parent lock. The existing `list_items_touch_list`, `lists_set_updated_at`, and `lists_refuse_armed_cover` triggers must be reconciled explicitly. Replace item-touch behavior with coherent parent locking/content revision and derived activity time; do not double-bump root metadata revisions or capture half-states. Derived updated_at-only activity is not a new root-content version. Retain armed-cover fencing. Root Trash does not rewrite every item. Root+content observations make reorder, membership refresh and future transfer conflict checks coherent. Original row columns/notes stay exact; there is no catalog/media inventory/backfill operation.

Use private append-only history:

- `family_auth.collection_root_versions`: `(collection_id uuid,revision bigint)` primary key, root FK RESTRICT, schema_version smallint=1, recorded_at timestamptz, actor_user_id uuid nullable FK RESTRICT, validated root `snapshot jsonb` object.
- `family_auth.collection_item_versions`: `(collection_id uuid,item_id uuid,revision bigint)` primary key, composite item FK RESTRICT, schema_version smallint=1, recorded_at timestamptz, actor_user_id nullable FK RESTRICT, validated base `snapshot jsonb`, nullable typed-content `location_snapshot jsonb` (unused until the later content migration).
- `family_auth.collection_root_version_media`: `(collection_id,revision,media_asset_id)` primary key; composite FK to root_versions and media FK to media_assets, both RESTRICT.
- `family_auth.collection_item_version_media`: `(collection_id,item_id,revision,media_asset_id)` primary key; composite FK to item_versions and media FK to media_assets, both RESTRICT. These are two concrete junctions, not a nullable polymorphic target. No copied signed URL. Root cover history participates immediately; item-location media joins when the child exists.

Capture the old committed row at its original revision before its first edit, then the final committed state after the transaction. Deferred capture must coalesce parent/child edits into one version, not store an intermediate half-snapshot. Rollback creates no versions. Do not create artificial history for untouched legacy rows. Preserve full retained text rather than truncating it to a new API limit. UPDATE/DELETE/TRUNCATE of history is refused; all direct privileges on new private history/state/receipt tables are revoked from PUBLIC, anon, authenticated and service_role. Reads go through checked entry points.

Every new FK needs a matching leading-key/partial index. In particular: deleted actor, lists(family_id,deleted_at DESC,id) for root Trash, list_items(list_id,deleted_at DESC,id) for item Trash, history lookup by item/revision, receipt target/actor, and media-reference lookup. Keep the17 existing indexes and eight all-state typed uniqueness rules. A trashed source is reserved for explicit Restore; a new save must not create another item that bypasses its retained identity.

### 2.2 Location-content extension — implemented locally by C2

Commit an enum-only migration adding `manual` to `public.list_item_kind`; then a separate transactional content migration. Generate names with the installed CLI, never invented timestamps. Extend both existing target checks: manual requires **zero** of the eight FKs; every other kind still requires exactly its matching one. Add a deferred consistency trigger requiring a location child for manual items. Optional children are allowed only for `place`, `food`, `hotel`, `experience`, `manual`. Existing other four item kinds and reference-only items are unchanged.

`public.list_item_locations` has:

- `item_id uuid PRIMARY KEY`, `list_id uuid NOT NULL`, `family_id uuid NOT NULL`.
- FK `(item_id,list_id)` → list_items(id,list_id) RESTRICT; FK `(list_id,family_id)` → lists(id,family_id) RESTRICT. This enforces tenant/category scope without backfilling a redundant tenant column into every old item.
- `description text NULL`, `latitude numeric(10,8) NULL`, `longitude numeric(11,8) NULL`, `address text NULL`, `website text NULL`, `phone text NULL`.
- `family_place_category_id uuid NULL`, FK `(family_place_category_id,family_id)` → family_place_categories(id,family_id) RESTRICT.
- `cover_media_id uuid NULL REFERENCES media_assets(id) ON DELETE RESTRICT`.

The item owns the saved name (`list_items.name`) and personal notes (`list_items.notes`); do not duplicate either in the child. A materialized/manual item requires a nonblank trimmed name of at most500 characters. New description/notes allow NULL or exact text up to20,000 characters; empty text is an explicit empty snapshot, not a request to re-inherit catalog text. Preserve internal whitespace/Markdown. Address≤2,000, website≤2,048 and canonical HTTP(S), phone≤100. Coordinates are a nullable pair, normalized to the declared eight-decimal precision **at observation time**, with latitude[-90,90], longitude[-180,180]; invalid/missing coordinates never become a city point. The original catalog digest still detects a source edit. No additional rounding is hidden during execution.

Presence of the child means `content_mode=snapshot`: child NULL/empty values stay NULL/empty. Absence means `content_mode=reference`: only the legacy typed catalog projection is inherited. New readers distinguish both; old readers must not silently discard a snapshot in favor of a newer catalog name/image. Materialization uses canonical observed source data or explicitly validated manual input, not arbitrary fields supplied with a source ID.

At this stage replace the eight catalog target ON DELETE CASCADE FKs with ON DELETE RESTRICT, preserving targets, names/validated integrity and source-kind checks. The preceding recovery trigger already prevents cascade data loss. Archive catalog sources instead of destroying saved content; a future approved purge is separate. Do not edit catalog records to make a Collection save fit.

Media must be retained by active/trashed content **and all versions**, including root cover versions. Integrate new reference relations into the existing private-media reference/cleanup protocol, keep exact media IDs, lock/check armed deletion state and refuse a new reference if byte deletion was already authorized. Reuse the reviewed armed-object fencing pattern; a metadata FK alone does not stop a Storage worker deleting bytes. Rehearse that race before enabling snapshot media. Ready-v1 object URLs are resolved from IDs at read time; missing/unready bytes are placeholders, never transformations or automatic originals. New arbitrary/manual image URL uploads remain unavailable until a qualified media contract exists.

## 3. Authority and original operations

Preserve existing list business rules: private list read/item edit belongs to its owner; active Family-visible list items are editable by active members; root metadata/archive belongs to its owner or a reviewer of a Family-visible list; super-admin access remains explicit. Creating/changing to Family visibility still requires reviewer/super-admin authority. Trip write permission is separate and cannot grant list access. A normal actor must have current active membership/person context; a global super-admin is not forced into an invented Family person. Required creator-person constraints for existing create/add behavior stay explicit.

All access also requires a live `auth.sessions` row for the claimed user/session, no expired `not_after`, and the existing role-sensitive private-assurance/MFA policy. Do not use user_metadata. Replace `can_view_family_list`, `can_edit_family_list_items`, `can_admin_family_list` **in place**, preserving OIDs/signatures and existing grants so policy/Storage dependencies cannot keep calling an unchecked renamed function. Use an unexposed checked helper with fully qualified identifiers/search_path=''. Raw SELECT excludes trashed roots/items and requires current session/assurance; recovery reads use a separate owner/editor/reviewer rule and never a permissive fallback. Archived/trashed history and Restore have explicit authority; ordinary root admins do not gain a new public share feature.

`family_auth.collection_operation_receipts` stores existing-target lifecycle operations initially: actor_user_id, operation_id, family_id, collection_id, original session_id (retained value, **no FK to a revocable session**), nullable original person_id, action, request_sha256 bytea length32, status (`committed`/`cancelled`), immutable result object and created_at. Primary key `(actor_user_id,operation_id)` prevents reuse across another list/Family. Family/list/user/nonnull person ownership FKs are RESTRICT. Never return session IDs, request digests or private request bodies through history/outcome projections. General root creation gets its own observed contract before legacy creation is retired; do not couple its entity UUID to an operation UUID by accident.

Acquire a transaction advisory lock for actor+original operation before target locks. Reusing an operation with different immutable context/observations/values is PT409. A committed replay rechecks current authority and returns only the original historical acknowledgement; it does not overwrite a newer canonical view. A new session resolves an owned outcome through the dedicated lookup, never by borrowing the old session scope. A missing receipt is `unknown`, not proof the request failed. Cancellation serializes with execution and records a tombstone for that exact original; it never rolls back an already committed action.

For lifecycle commands first preflight current session/authority, acquire the list root, then pin and recheck Auth session/profile/membership/person/MFA authority before sorted item rows and mutation. Do not hold authority locks across the initial root wait: a committed revocation during that wait must become visible. Recheck authority after waits and immediately before mutation. Tests must reproduce revocation while waiting; if a stable helper sees an old snapshot, correct the implementation rather than weakening the race test. New cross-aggregate transfers always lock list before Trip, regardless of direction, then sorted child/source/media rows. Use FOR SHARE when source facts must not change during materialization; KEY SHARE alone does not freeze mutable text. Root identity/family/list/source tuples cannot be reassociated. Keep locks bounded and avoid calling independent public commands that commit only part of a transfer.

Existing service-role grants are inventoried and preserved unless a specific change is explicitly reviewed; never make a blanket grant/revoke. Retention DELETE/TRUNCATE guards still apply. Harden `create_family_list` in place as well: it does not call the list predicates before creating a new root and therefore needs the current-session/private-assurance gate directly, preserving its name/color/visibility/person rules. Unversioned browser writers must not bypass an observed cohort. The immediate packet retires physical `remove_list_item`; other legacy mutators are explicitly inventoried/hardened and must be retired or restricted before a competing new writer is enabled. Root create/update/cover cutovers are separate, not implicit new capabilities of recovery.

## 4. Versioned API surfaces

The nine subsection4.1 recovery names/signatures are installed and locally qualified by C1; subsection4.2 remains **planned**. Neither means hosted/native availability. Public functions are thin SECURITY INVOKER wrappers over unexposed, fully checked entries where that matches the existing pattern. Grant authenticated only the wrapper and checked entry/predicate actually required; unchecked helpers, triggers and tables remain inaccessible. Explicitly revoke default PUBLIC/anon execution on every new routine. No service key enters the browser.

### 4.1 First implementation: recovery/context, not transfer

- `get_family_collection_context_v1(p_collection_id uuid,p_state text DEFAULT 'active') RETURNS jsonb`.
- `get_family_collection_item_context_v1(p_collection_id uuid,p_item_id uuid) RETURNS jsonb`; exact scoped item metadata under the applicable active/recovery authority.
- `list_family_collection_trash_v1(p_family_id uuid,p_limit integer DEFAULT 50,p_before_deleted_at timestamptz DEFAULT NULL,p_before_id uuid DEFAULT NULL) RETURNS jsonb`.
- `list_family_collection_item_trash_v1(p_collection_id uuid,p_limit integer DEFAULT 50,p_before_deleted_at timestamptz DEFAULT NULL,p_before_id uuid DEFAULT NULL) RETURNS jsonb`.
- `execute_family_collection_lifecycle_v1(p_collection_id uuid,p_operation_id uuid,p_scope jsonb,p_action text,p_expected_revision bigint) RETURNS jsonb`; action only `trash`/`restore`.
- `execute_family_collection_item_lifecycle_v1(p_collection_id uuid,p_item_id uuid,p_operation_id uuid,p_scope jsonb,p_action text,p_expected_revision bigint,p_expected_collection_revision bigint) RETURNS jsonb`; action only `trash`/`restore`.
- `list_family_collection_versions_v1(p_collection_id uuid,p_item_id uuid DEFAULT NULL,p_limit integer DEFAULT 25,p_before_revision bigint DEFAULT NULL) RETURNS jsonb`; NULL item selects root versions, otherwise the scoped item. Limit1..100, positive complete before-revision cursor, descending revision; current recovery authority, no actor-user/session/digest leakage. Restoring an old edited version is a later explicit observed command, not silently included in Trash Restore.
- `get_family_collection_operation_v1(p_family_id uuid,p_operation_id uuid) RETURNS jsonb`.
- `cancel_family_collection_operation_v1(p_family_id uuid,p_operation_id uuid,p_original jsonb) RETURNS jsonb`; p_original is the exact bounded lifecycle request, not an unchecked replacement digest.

Root context is metadata-only `{version:1,scope,collection,collection_revision,content_revision,item_counts}`. `collection` contains IDs, revisions, lifecycle/archive/deletion state, visibility and owner identity, not descriptions or item bodies. Item context adds one scoped item's IDs/kind/source/revision/status/order/deletion metadata, not its full notes/body. This lets an oversized legacy collection still obtain a safe Trash/Restore observation without first loading its entire content. Scope has exactly `version`, `family_id`, `collection_id`, `user_id`, nullable `person_id`, `session_id`, `lifecycle_revision`; UUIDs/current authority/assurance come from the validated context, not user-supplied identity. `p_state` is active/archived/trash; no implicit fallback. Metadata contexts are at most64KiB; overflow raises54000 rather than truncating. Later content reads have their own explicit paging/size contract; no fake empty `items` array represents unrequested content. Trash/history pages are at most8MiB, limits1..100, ordered `(deleted_at DESC,id ASC)` or revision DESC, complete finite cursors and limit+1 lookahead. Active rows never consume the Trash retention budget.

Success returns `{version:1,operation_id,status:'committed',action,target_kind,target_id,revision,collection_revision,content_revision,changed}`. It is an acknowledgement, not a native Place response or fresh canonical publication. A correctly observed redundant Trash/Restore is changed=false with no revision/history bump. A stale observation refuses even for an apparently redundant request. Same-original retries return the historical acknowledgement. Outcome lookup returns unknown/committed/cancelled and a bounded redacted acknowledgement only; it can resolve a lost reply after authorized lifecycle/session changes without returning old private content. Unknown lookup cannot authorize a new operation ID.

Use42501 for inaccessible/current authority/session failures,22023 for malformed/unknown fields or invalid cursors, PT409 for stale/conflicting/reused observations,54000 for bounds,0A000 for deliberately unimplemented lifecycle/legacy physical removal. The Family transport maps these to its existing explicit error conventions; do not treat unique violation as authorized success. No mutation acknowledges before the final history/receipt write; late failure rolls everything back.

### 4.2 Later content/transfer slice

After child storage and observed create/update/status/reorder commands pass, add:

- `get_family_collection_membership_v1(p_family_id uuid,p_identity jsonb) RETURNS jsonb`. Identity is exactly a canonical `{kind:'place'|'food'|'hotel'|'experience',id:uuid}`, a saved `{trip_id,location_id}` resolved under current source permission, or an owned manual-transfer origin. Names, coordinates and provider strings are not identity. Membership is complete/bounded (maximum200 visible matching lists,2MiB; overflow refuses). Return UUID entries with status/can_edit; the client maps IDs to the native `{saved,lists:[{collection_id,name,color,place_id,status,can_edit}]}` envelope.
- `get_family_collection_transfer_context_v1(p_direction text,p_collection_id uuid,p_trip_id uuid,p_source_ids uuid[],p_layer text DEFAULT 'published') RETURNS jsonb`.1..100 unique source IDs, same Family, current source reads and destination permission; v1 explicitly refuses non-published layers rather than falling back. Return exact list/Trip lifecycle/revision, item/location observations, materialized canonical snapshots and possible destination observations.
- `execute_family_collection_transfer_v1(p_operation_id uuid,p_scope jsonb,p_observed jsonb,p_values jsonb DEFAULT '{}') RETURNS jsonb`. Direction is in the frozen scope, IDs/revisions/digests are in strict observations, destination Collection status is the only optional transfer value in the first slice. Unknown/reassociated/arbitrary native fields refuse. This command joins both halves in one transaction and shares the retained-original discipline; it does not call the old geography copy helper.

From Trip, read the actual saved location and its typed source. Copy its **effective** label/description/address/coordinates/category and Trip-location notes into independent Collection content. Do not copy scheduled-visit notes, reservations or whole native payloads. A source form's mismatching fields are a conflict, not fields silently dropped. Bare manual input needs its own validated create contract; a provider ID is not secretly a catalog or manual source.

To Trip, copy into the saved-location pool only. It schedules **zero visits**; the existing qualified Add-to-day workflow creates independent repeated visits. Catalog pool uniqueness is retained. An identical existing destination yields an explicit existing outcome, never an overwrite; different destination notes/details/media yield destination_conflict. A trashed matching item/location yields restore_required. `force:true` from native callers never bypasses Family uniqueness/permissions or overwrites saved content.

For manual Collection items use a private origin relation keyed `(collection_item_id,trip_id)` to an existing normalized Trip location (composite location/Trip FK), plus observed revision. Another explicit pool copy reuses that exact relation if content still agrees; never deduplicate by name/distance. A changed/deleted destination refuses; no hidden clone/restore. Multiple visits are separate regardless of pool reuse. New operations and same-original retries are not interchangeable.

Trip locations currently cannot express every frozen image/price detail. Preflight every field against the actual destination contract. Do not claim unsupported nonzero price, custom/manual image URL or a historical cover different from the representable current catalog cover was copied. Return content_not_representable before any write; expand the typed Trip media contract in a separate packet if required. Native compatibility zero/default-currency placeholders are not newly stored financial facts. Preserve ready-variant identities and explicit View original; no transformation fallback.

Bulk admission is atomic: reject a missing/inaccessible/conflicting/unsupported item before the first mutation. A historical receipt is never a fresh skipped/copy result. Root/library creation, non-location catalog transfer, labels, invites, sharing, ratings and Tours are not enabled by these APIs.

## 5. Native consumer and release gates

The native membership hooks currently swallow errors and omit typed source identity. Before enabling any toggle, wire exact identity at the non-presentational data boundary and share loading/unavailable/retry state across inspector, desktop picker and phone sheet. A failed membership read must not select Add/Delete from a fabricated saved=false. Shared native save/copy hooks must consume the actual created/existing/conflict result; no success toast for a refusal, no lost note/draft and no version bump on error. Keep existing layouts/styles and12 protected files exact.

Lifecycle/API availability is not an owned Restore user flow. Before enabling native removal, prove a reachable authorized recovery control using the existing Family recovery integration pattern, including archived parent behavior. Do not offer destructive Delete while Restore is unreachable. Keep current transfer refusals until actual DB/Auth/SDK/queue/native-browser tests pass for the whole selected slice.

Deployment remains blocked on coordinated readers/writers/retained queue and schema, not merely a passing database migration. Separate source-adoption pins/default-profile/hosted engine/schema/recovery/publication gates remain. No production settings/billing/schema or preview deployment is authorized by this design packet.

## 6. Technical basis and reference files

PostgreSQL enforces cross-row referential relationships with FKs, not table CHECK expressions; deletion actions must preserve owned content. [PostgreSQL17 constraints](https://www.postgresql.org/docs/17/ddl-constraints.html). New enum labels require a committed boundary before use. [PostgreSQL17 ALTER TYPE](https://www.postgresql.org/docs/17/sql-altertype.html). RLS and function grants must both enforce caller authority; elevated functions use a restricted search path. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [database functions](https://supabase.com/docs/guides/database/functions).
