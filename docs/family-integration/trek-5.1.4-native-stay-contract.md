# U05-B2b3c5 — native stay transaction contract, schema 135

The database portion is locally qualified on a fresh isolated schema-134 derivative using the final plain schema-135 migration. This is an implementation contract, not a deployed API or qualified native UI. Preserve the accepted C4 client/service, source adoption 5.1.2 and exact upstream 5.1.4 layouts until the client phase passes.

Native TREK creates a stay, partner booking and arrival assignment in one transaction. Only arrival gets a real occurrence; later-night bookends are derived from the stay. A previously planned visit at that lodging/day is reused without being claimed. `keepStop` releases an owned arrival as an independent occurrence. Native Nest deletion of bookings/expenses is deliberately replaced by recoverable Family Trash, preserving independently owned content.

The normalized extension is nullable `schedule_items.owning_stay_id`, a restrictive FK to `trip_stays`, one partial unique index, and a trigger enforcing same-Trip untimed ownership. Independent occurrences remain NULL. Creation/movement/lifecycle of owned visits is permitted only in a narrowly controlled transaction context, never a caller-set GUC. Ordinary visit notes/duration/order remain their own facts. No country/city identity substitutes for a saved lodging or visit. Existing export emits complete schedule records, so this relationship is included without rewriting the old export API.

A separately tagged `family.native-stay.v1` command contains exact `operation_id`, `scope`, `stay_id`, `inner`, `arrival_visit_id`, `keep_stop`, and `observation` fields. The complete inner command is the existing strict stay-bundle creation or an existing observed save/Trash/restore; identity/scope copies must exactly agree. The proposed new visit UUID is fixed before retention, distinct from the operation/stay/booking, and is used only when no suitable existing arrival exists. Unknown fields or a command over2MiB are refused; the inner command keeps its own existing bounds.

`get_family_native_stay_context_v1(inner, arrival_visit_id, keep_stop)` validates the current actor/session/domains and exact original inner observation, then returns the complete outer command with original arrival-day ordered observations and complete owned-visit facts. It does not write content or enable native controls. No observed fact is silently refreshed during a retry.

`execute_family_native_stay_v1(command)` locks the original Trip, current session/Family/person and relevant visits, rechecks authority after waiting, validates both observations, then executes the existing stay command and the arrival changes in one transaction. It retains the original inner receipt and one outer decision in the existing immutable location receipt ledger. Independent intent from those namespaces cannot be adopted as partial native success. The outer receipt binds the whole request, including the proposed visit and `keep_stop`. A final failure rolls back stay, booking/calendar/link, visit/order, revisions, both receipts and audit together. Sequence gaps from rolled-back `nextval` remain normal PostgreSQL behavior.

A stay's local check-in is seating guidance; the created arrival remains untimed with NULL appointment timestamps and zone. Known midnight, seconds, named zones and overnight stay windows are retained. Seating follows pinned upstream order: unknown check-in leads ordinary unclocked places; known clocks follow the last qualifying earlier stop; stays with equal guidance settle by creation time and UUID. Other visits' relative order remains intact. No legacy timestamp is guessed into an appointment or geography-based zone.

When an owned arrival is also serving another active stay, moving/removing its original stay releases that occurrence rather than removing another stay's route. When moving onto an independent existing visit, the old owned occurrence is recoverably trashed and ownership is released; the existing visit is not overwritten. Normal Trash retains owned arrival identity and independently owned booking facts. Restore recovers the original owned visit, or reuses an independently released visit without reclaiming it.

`get_family_native_stay_outcome_v1` and `cancel_family_native_stay_v1` accept the complete original outer command. Current same-actor fresh sessions can inspect/cancel, never rewrite the old write session. Cancel also tombstones the exact inner operation, so it cannot later create half the user action through an older API. Receipt reads still require current domains: schedule+reservations for creation; schedule for save/Trash/restore. No failure becomes fake unknown/success.

`get_family_native_stay_view_v1(trip)` returns a separately tagged wrapper around one STABLE coherent core with explicit `owning_stay_id` only on active owned arrivals. The original v2 read remains unchanged. Fresh current authority is checked before and after the snapshot. Native/cache projections must validate each association and preserve it in the complete core before publishing; no heuristic location/date join may invent ownership.

`list_family_trashed_stays_v1(trip, after, limit)` is a current-session, current-Direct-schedule API. Limit1..50; keyset cursor is exact finite `{deleted_at,id}`; ascending `(deleted_at,id)` uses the existing partial Trash index. Pages expose identity, revision, dates, label, deletion time and explicit restoration availability. An archived/trashed lodging is shown as unavailable, not falsely restored. A trashed parent Trip, foreign member or insufficient assurance fails. The UI must expose this independently of unresolved queue recovery, including cross-device discovery.

The frontend portion must use one retained whole outer command, exact metadata ownership and outcome-first retry; refresh the coherent core and real ancillary resources before native/cache publication; retire source/session/layer/registry changes; and expose Add/removal only with reachable restoration. No frontend code or feature flag is activated by this database migration alone.


## Exact public RPC and response boundary

The only new authenticated public functions are:

- `get_family_native_stay_context_v1(p_inner jsonb, p_arrival_visit_id uuid, p_keep_stop boolean default false)`; response `family.native-stay-context.v1`, with `command` and `native_controls:false`.
- `execute_family_native_stay_v1(p_command jsonb)`; response `family.native-stay-ack.v1`, with `acknowledgement:true`, `read_current_required:true`, original `trip_id`, `stay_id`, `operation_id`, actual `trip_revision_after`, nullable `arrival_visit_id`, and `action`.
- `get_family_native_stay_outcome_v1(p_command jsonb)` and `cancel_family_native_stay_v1(p_command jsonb)`; strict original-command decision inspection/cancellation.
- `get_family_native_stay_view_v1(p_trip_id uuid)`; wrapper `family.native-stay-view.v1` containing `core`, which remains the coherent booking/stay core with explicit arrival ownership.
- `list_family_trashed_stays_v1(p_trip_id uuid, p_after jsonb default null, p_limit integer default 25)`; response `family.stay-trash.v1`, original `trip_id`, `items`, `has_more`, `next_cursor`.

The outer observation is exactly `{trip_revision,day_id,location_id,owned_visit,day_visits}`. Each day observation is `{id,revision,order,location_id,timing_kind,starts_at,time_zone,owning_stay_id}`. `owned_visit` retains the complete original schedule row or NULL. The full command is bounded at 2 MiB, inner at 1 MiB, coherent native core at 8 MiB; do not weaken existing bounds to admit partial content. Context generation is initial preparation, not permission to rebase an unresolved command.

No-op native saves can return the unchanged Trip revision. Validate `trip_revision_after >= observation.trip_revision`, not an invented increment. The older create-bundle acknowledgement remains its own stricter dialect. Cancellation/inspection cannot become an automatic execute, retry cannot allocate a new operation/arrival/stay/booking identity, and an old-session retained command cannot be rewritten to the fresh session.

The transaction context is one private RLS-enabled table keyed by `(transaction_id,trip_id)` and actor, empty after successful commands; it is not another business or recovery store. Ownership has a restrictive FK and one partial unique index. Same-Trip/untimed/lifecycle invariants are enforced by triggers in all write paths. Clients cannot set that context or ownership column directly. All 17 added functions are owned by normal non-superuser `postgres`, use an empty search path, and deny anon/service-role execution; only the six public functions grant authenticated execution. The 595 earlier function definitions, owners and ACLs are exact.

Old stay/day/visit writers deliberately refuse a change that would desynchronize an owned arrival. The coordinated client phase must route affected actions through the compound operation before activation. A legacy-timed arrival-day record is refused for seating until explicitly classified; never guess or rewrite its timing.
