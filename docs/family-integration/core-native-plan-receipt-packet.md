## Exact contract

`get_family_native_plan_receipt_v1(p_trip_id uuid,p_operation_id uuid,p_scope jsonb,p_form jsonb)` accepts the exact creation scope/form with the existing180000-byte bound. Scope is version1 plus trip/Family/user/person and explicit published/myDraft layer. Form has exactly location/day/clocks/visit_notes. Use the existing digest `sha256(convert_to(jsonb_build_array('native_plan_create',p_scope,p_form)::text,'UTF8'))`. No caller-selected domain/table, reconstructed request or source URL is accepted. Source ownership is the future adapter's separate fence.

Require current private session, active Family/person, Trip assurance and the same current shape-specific direct location/schedule permissions (published) or location/visit stage permissions (myDraft) as creation. Check authority before both unknown and committed responses. Select only current Trip/actor/operation. An existing own receipt with a different digest/domain is a conflict; another actor's receipt is never exposed. Recheck private session before returning. A later authorized login can inspect the same original; session tokens/identifiers are not part of that original.

Return version1, trip_id, operation_id, validated original scope, status unknown|committed and result null|original creation receipt. Unknown adds nothing. Published results remain historical acknowledgements; refresh canonical state before UI publication. For myDraft, use the existing pure plan_stage_state projection so committed/removed is distinct from unknown. Never recreate an entity or infer success from current content.

Private family_auth.native_plan_receipt is STABLE SECURITY DEFINER with empty search_path and postgres owner, with explicit authorization. Public wrapper is STABLE SECURITY INVOKER, empty search_path. Revoke default function execution from PUBLIC/anon/authenticated/service_role, then grant only both required function EXECUTEs to authenticated. Existing private-schema USAGE stays exact. No table grant or new index: the existing composite receipt key supplies the lookup. The reader must succeed inside actual READ ONLY transactions, without row/advisory locks, writes, cancellation or calling a command.
